## 1. 威胁模型与实测中毒面（比任务书更凶的三条）

任务书四论断经实测全部属实，且实测发现**三条更凶的机制**，先立此为据（行号可抽验）：

### 1.1 任务书四论断实测复核

1. **锁全是 std + expect**：内核 `.lock().expect(...)` / `.read().expect(...)` 遍布 8 个文件 30+ 处——fiber 决策锁（每 fiber 一把，fiber.rs:162/228、load.rs:62/166、ops.rs:42/61/110）、fiber 表锁（全局，context.rs:99、registry.rs:84/110）、服务表锁（全局 RwLock，load.rs:39/171、service.rs、ops.rs）、dependents 锁（每服务条目，load.rs:275、service.rs:202/257/269）、监听表锁（全局，events.rs:146/155/162）、waterfall 表锁、isolate/intercept 锁（每上下文，context.rs:123/130）、agent-loop 事件缓冲锁（observer.rs:127/133）。全部 std::sync，全部 `expect` 直炸。
2. **catch_unwind 零命中**：`grep -rn catch_unwind crates/` 零结果。`Tool::execute` 返回 `BoxFut<'static, ToolOutcome>`（tools/contract.rs:153）、`Plugin::setup` 返回 `BoxFut<'static, Result<FiberOutput>>`（registry.rs:61）——同步 catch_unwind 包 BoxFut 包不住 Poll 期 panic，属实。
3. **panic profile 未钉死**：Cargo.toml `[profile.release]` 仅 `lto = "thin"`，无 panic 设置；全仓无 `.cargo/config`、无 CI workflow 目录。当前默认 unwind 属**侥幸**，任何人写 `panic = "abort"` 即静默失效全部隔离机制。
4. **一处中毒全线陪葬**：std Mutex 中毒后 `lock()` 恒返回 `Err(PoisonError)`，所有 `.expect()` 连环 panic，且**中毒永不清除**（自愈不存在）。

### 1.2 实测新发现（设计必须一并回答）

**凶点一：setup panic = 幽灵 Loading（无收尸）。** 装卸任务里 `plugin.setup(ctx, resolved).await` 直接 await（load.rs:202）。setup 的 BoxFut 在 Poll 期 panic → panic 沿 await 沿传播、击杀整个 `run_load` 任务（tokio 只把任务变成 JoinError，`spawn_load` 的 spawn 无人 join 检查）→ `prepared` 收尾逻辑（load.rs:212-237，含 `finish_load_error` 置 Failed）**永不执行** → `core.busy` 恒 true、fiber 永卡 `Loading`。没有 Failed 转移、没有清理、没有通知——比崩溃更隐蔽的僵尸。

**凶点二：中毒锁经扫描路径跨 fiber 击穿无辜者。** 决策锁虽是每 fiber 一把，但 `notify_services`（registry.rs:110）在服务表变更时**扫描全部存活 fiber** 并逐个 `drive()` → `lock_core()`。于是：插件 A 的 provide 注册体 panic（注册体在 A 的决策锁内同步执行，effect.rs:101-116 `execute()?`）→ A 决策锁中毒 + A 的 run_load 任务死亡（凶点一）→ 此后插件 B 正常卸载触发服务表变更 → `notify_services` 扫到 A → `drive` → `lock_core` expect 炸 → **panic 炸在 B 的卸载链上**，B 卡 Unloading。一个坏插件永久毒化扫描总线，全主板逐个陪葬——这就是「一处中毒全线陪葬」的完整机制。

**凶点三：waterfall 链无 panic 边界。** `ChainCursor::advance` 在当前任务内直接 `listener(&args, next).await`（waterfall.rs:44-51），无 spawn。插件监听器 panic 会炸穿瀑布任务——而 `internal/update` waterfall 的内置行为是 `restart`（ops.rs:106-118），即配置更新流可被一个坏监听器打死。

### 1.3 已有的防护先例（本设计的复用基础，不是从零造）

| 先例 | 位置 | 机制 |
| --- | --- | --- |
| 工具执行 panic 边界 | tools/executor.rs:32-43 | `tokio::spawn` + JoinErr → `tool/panic` 错误归一；select 三路（结果/超时/取消） |
| 事件监听器边界 | events.rs:96-129（parallel 用 JoinSet，serial 用 `tokio::spawn` 逐个） | 注释明说「单个监听器 panic 不会击穿分发」；emit 先快照后 spawn，监听表锁不跨插件代码 |
| disposer 清理边界 | load.rs:250-258、287-295 | 单个 disposer panic 不阻断逆序清理 |
| 取消合并 | agent-loop/cancel.rs（S7-R1 范本） | 两源合一 child token + CancelBridge 防孤儿 |

**结论**：仓库的既定事实是「**tokio 任务边界 = panic 边界**」。本设计把它从三处实践升格为全内核纪律，而不是引入新机制。

## 2. 锁中毒破局（一题：三案对比裁决）

### 2.1 三案对比

| | 案① parking_lot 全局替换 | 案② SafeLock 封装（poisoned.into_inner 强取） | 案③ 缩粒度（dashmap/RwLock） |
| --- | --- | --- | --- |
| 消灭连环炸 | **根治**：不中毒，锁内 panic 不污染锁，后续 lock() 正常 | 不根治：锁照旧中毒，炸变「强取带撕裂状态继续跑」 | 不根治：只缩小波及面 |
| 消灭 expect | **顺带根治**：`.lock()` 直接返回 guard，30+ 处 expect 消失 | 不能：SafeLock 自身是第三种锁概念，调用方还要学 | 不能 |
| 数据一致性 | 持锁 panic 后状态由 panic 边界案（§3/§4）收敛为 Failed，无撕裂 | **致命伤**：决策锁临界区是多字段不变量（epoch/busy/effects/provisions，fiber.rs:67-88），panic 在半程时强取=带撕裂状态运行，比崩溃更难排查 | 不变量不因缩粒度而消失 |
| 工程成本 | 机械替换（用法面全部是 `.lock().expect(...)`/`.read().expect(...)`/`.write().expect(...)`，parking_lot 同名方法直接可用）；**依赖已在树中**（Cargo.lock:923 parking_lot 0.12.5，间接依赖在用，加直接依赖零新增编译负担） | 新写锁类型+全仓替换调用点+声明「仅止血」+**将来还要再改一遍**（双倍工时） | fiber 决策锁是复合不变量（epoch 重算需原子多字段视图），dashmap 不适用；换数据结构=并发语义重审，成本最高 |
| 性能 | parking_lot 自旋+futex，无争用时优于 std | 无收益 | 仅在读多写少且有实测热点时有收益 |

### 2.2 裁决

**采纳案①（parking_lot 全局替换，内核 crate 范围）**，理由：

1. 根治中毒（不中毒）＋顺带根治 expect（API 无 PoisonError）——**这是 §2.4 lint 红线能落地的先决条件**：std Mutex 的 `lock()` 必须处理 `LockResult`，expect 是最惯用解法，不改锁类型则 `deny(clippy::expect_used)` 无从谈起。两案互为条件，一起裁决。
2. 依赖零新增负担（已在依赖树）；API 兼容（仓库无任何代码依赖 `PoisonError::into_inner`/`is_poisoned`/`TryLockError` 模式，已 grep 确认）。
3. **不需要薄 wrapper**：替换直接用 `parking_lot::{Mutex, RwLock}` 具体类型。为 v2 留缝：内核新增 `src/sync.rs` 统一 re-export（`pub use parking_lot::{Mutex, RwLock};`），全内核从该模块引锁类型——未来子进程隔离版若换实现，只动一处。
4. 案②不采纳：它把「崩溃」变成「静默数据撕裂」，与业主令意图（崩得干净、可恢复）相悖；且是过渡方案=双倍工时。仅在一种情况下考虑：若案①替换因外部原因被冻结，作为 P0 紧急止血的**临时**手段，且仅限单字段锁——本设计不排此案。
5. 案③不采纳（本轮）：内核锁全部是低频锁（装卸/注册/事件表增删），无实测热点证据，先不缩粒度——与改造方案 §6「规模优化留待出现热点时再做」口径一致。两个具体评估结论留档：fiber 表锁（registry.rs:110 全量扫描+retain）若未来成为热点，dashmap 可评估（读写比：注册时写、扫描时读改，频率∝插件装卸，一期极低）；服务表已是 RwLock，parking_lot 化即可。fiber 决策锁**不可** dashmap 化（epoch/busy/effects/provisions 是原子复合不变量）。

### 2.3 std 特有约束核对（案①的注意事项，实测过）

- `lock()` 返回类型：std `LockResult<Guard>` → parking_lot 直接 `Guard`。仓库所有调用点都是 `.lock().expect("...")` 形态，替换后删掉 `.expect(...)` 即可，无其他形态。
- `RwLock::read/write` 同上。
- `Arc<Mutex<T>>` 的 `clone`/`lock` 用法不变；`parking_lot::Mutex` 也实现 `Default`/`Debug`（与 std 一致）。
- 无 `Condvar`/`Once`/`Barrier` 使用（grep 确认），无跨锁类型 trait 边界。

### 2.4 规范红线（业主深化：lint 硬门 + Fatal 状态机）

1. **lint 硬门**：`crates/yunyou` 与 `crates/yunyou-agent-loop` 挂 `#![deny(clippy::unwrap_used, clippy::expect_used)]`，测试模块（`#[cfg(test)]` 与 `tests/` 目录）豁免。现状内核 `.expect`/`.unwrap` 约 50 处：大头是 `.lock().expect`（案①替换后自然消失），余量逐个改为 `?`/`ok_or`/显式错误——实施批 S-ISO-1 内清完，lint 上线当日必须零残留。
2. **Fatal 状态机（不可恢复错误不 panic 炸现场）**：新增 `error::FatalKind`（root fiber 崩溃 / 内核不变量破坏 / 启动期装配致命错）＋统一入口 `fatal_exit(kind, msg)`：刷日志与事件缓冲 → 通知所有 fiber 收流（root cancel）→ 进程以非零码退出。**红线**：内核主干代码禁止以 `panic!`/`unwrap` 表达不可恢复错误；panic 只允许出现在「插件代码被边界捕获」的场景里。root fiber 自身的崩溃=主板崩，走 Fatal 优雅退出（不是 abort 轰炸现场，也不假装能隔离自己）。
3. **锁纪律不变**：现有「锁不跨 await」「锁序 core → services → default_scopes」「注册体内不得 lock_core」（effect.rs:93-95 注释）继续有效；parking_lot 不改变这些纪律。

## 3. async panic 边界（二题：两案裁决）

### 3.1 候选案

- 案 A：`FutureExt::catch_unwind` 包 BoxFut（在 poll 处捕获，`AssertUnwindSafe` 标注）。
- 案 B：executor 层 `tokio::spawn` + `JoinHandle` Err（`is_panic()` 判别）。

### 3.2 裁决：案 B 为主（统一任务边界），案 A 降级为同步回调面的辅助函数

1. **仓库已有三处案 B 实践**（§1.3），统一=承认既有事实并推广，不引入新概念；`JoinError` 自带 `is_panic()` 与 payload，错误归一信息完整（executor.rs:37-42 的 `tool/panic` 即成品范例）。
2. **案 A 的死穴**：对插件返回的任意 BoxFut 捕获 panic 必须 `AssertUnwindSafe`——这是对「panic 后状态安全」的自觉声明，插件代码任意写，声明无依据，等于逐处豁免编译器检查（家规反万能药条款不允）。案 B 的边界是任务隔离，panic 后整个任务状态机整体丢弃，不存在「半途状态被继续使用」的路径。
3. **案 A 的正当用武之地（保留）**：同步内核回调面——`effect_with` 在**决策锁内同步执行**插件注册体（effect.rs:101-116，provide 注册体经 service.rs 同路径）。这里是同步 `FnOnce -> Result`，不进 tokio 任务，只能 catch_unwind。处置：内核新增一个集中辅助函数 `catch_panic(f) -> Result<T, CordisError>`（内部唯一一处 `AssertUnwindSafe`，注释写明「仅限内核同步回调面使用」），在 `effect_with` 的 `execute()` 调用处包一层。parking_lot 化后锁不再中毒，但 panic 仍会传播出 `lock_core` 炸调用者——`catch_panic` 把这个出口收敛为 `Err` → Failed 转移。
4. **范围清单（全内核插件代码入口盘点，S-ISO-2 按此逐个落边界）**：

| 入口 | 现状 | 动作 |
| --- | --- | --- |
| 工具 `execute` | 已有边界（tool/panic） | 补专项测试（现无），零改动 |
| 事件 `emit/parallel/serial` 监听器 | 已有边界 | 零改动 |
| disposer 清理 | 已有边界 | 零改动 |
| **setup（run_load await）** | **裸奔（凶点一）** | `tokio::spawn` 边界：Ok(Ok)/Ok(Err)/Err(join) 三分支，panic 分支归一为 `PluginPanicked` 错误走 `finish_load_error` |
| **effect 注册体（锁内同步；provide 经同一 effect_with 路径但其注册体为内核代码）** | 裸奔（凶点二源头） | `catch_panic` 包 `execute()`（§3.2.3） |
| **waterfall 监听器** | **裸奔（凶点三）** | `advance` 内每环 `tokio::spawn(...).await` + JoinErr 归一 Err；串行序与重入防线（WaterfallReentry）语义不变——每环仍等前一环落定，`next()` 单次调用契约不受影响（实现期以 lifecycle 既有 waterfall 测试回归验证） |

### 3.3 与取消语义「等静止不 abandon」的影响评估（业主深化必答）

1. **spawn 边界不改变取消语义**。取消信号走 `CancellationToken` 通道，与执行容器无关：工具 future 在 spawn 的子任务里照旧监听 `exec.cancel` 自行收流（executor.rs 契约注释原样成立）。超时/取消分支走后 `JoinHandle` 被 drop＝**detach 不 abort**——任务继续跑到自身静止，正是「等静止不 abandon」语义（contracts.ts 对齐注释，executor.rs:13）。
2. **setup 加 spawn 的语义变化**：setup future 从装卸任务内联执行变为独立任务。两点论证无碍：(a) setup 期间本就不持任何内核锁（锁不跨 await 纪律），跨 worker 调度无锁危害；(b) 卸载取消经 `FiberShared.cancel`（fiber.rs:99）→ 组件按 §2.3 契约监听后静止，与内联执行时同一信号源。装卸收尾仍由装卸任务 `handle.await` 同步等待——**结构化等待保留，只隔离 panic**。
3. **catch_panic（同步面）无取消交互**：注册体契约本就禁止 await（effect.rs:95「锁内不得 await」），纯同步瞬时执行，无取消窗口。

## 4. panic=Failed 状态转移（三题：崩即卸载＋消费方不陪炸＋可重启用）

### 4.1 复用论证（业主深化必答：复用点逐条指认，不重建）

| 业主要求 | 复用机制 | 落点 |
| --- | --- | --- |
| panic 即状态转移 | `FiberState::Failed` 已存在；`finish_load_error`（load.rs:244-265）已完成「释放 committed 依赖登记＋唤醒提供者＋effect 逆序清理（带边界）＋置 error/epoch/busy＋set_state(Failed)」全套 | 崩溃只做一件事：把 panic 归一为 `CordisError{ kind: PluginPanicked }` 后**原样走 `finish_load_error`**（经 §3 的 spawn 边界三分支进入）。ErrorKind 增补 `PluginPanicked`，payload 携带 panic 信息（location + payload 字符串） |
| 自动完整卸载 | 同上的清理语义：本次注册的 effect 逆序撤销＋`release_committed_deps` 摘除依赖登记并唤醒提供者（service.rs:250-265） | 零新增 |
| 消费方「依赖未就绪」不陪炸 | strict 语义：提供者非 Active 其服务不可见（service.rs `get_strict`，load.rs:39-46 注释）→ `set_state(Failed)` 触发 Active 边界广播（load.rs:118-126）→ `notify_services` 扫描 → 消费方 fiber `drive` → epoch 重算 Inactive → `Unloading` → 收流等待 → `dependents` 清空 → `Pending`，诊断输出「依赖未就绪」（§5.3 验收第 1 条同款机制，已实测在位） | 零新增 |
| 在途对话轮优雅收流 | S7-R1 取消合并链：提供者 Failed → 消费方 fiber 被驱动卸载 → 消费方 `FiberShared.cancel` 触发 → `merge_cancel` 桥接（cancel.rs:14-31）→ 在途轮合一令牌取消 → 工具/LLM 收流静止 | 零新增（依赖 S7-R1 落地） |
| 可重启用 | `FiberHandle::restart()`（ops.rs:26 注释明说「FAILED fiber 的唯一复位手段」）：revision+1 → 清 error → drive → 原地重装。管理面（CLI 状态表/配置 toggle）接此 API | 零新增；二期可加崩溃计数＋自动禁用（熔断雏形，非本轮） |

### 4.2 语义辨析（防误读）

1. **Failed ≠ Disposed**。崩溃后 fiber 本体**保留**在表中、状态 Failed、可 restart——这正是「可重启用」的前提；`dispose`（uid 置空，ops.rs:120-136）才不可复活，崩溃路径**不调用 dispose**。
2. 「自动完整卸载」的准确含义＝**崩溃实例的资源卸载干净**（本次装载注册的 effect 逆序撤销、依赖登记释放、提供者被唤醒）＋ fiber 记账为 Failed 等待重启。不是把 fiber 从注册表抹掉。
3. **Active 期崩溃面收敛后不毒 fiber**：工具 panic（tool/panic）、监听器 panic（任务边界）都在 fiber 外被捕获，fiber 本体不受影响——需要 Failed 转移的只有 setup 期与注册体期两类，均由 §3 边界捕获后进入 4.1 链条。设置/装载期失败本就对应 Failed（fiber.rs:33 注释），崩溃只是其中一种 err 来源，语义自洽。
4. **「被超越」场景不误判**：spawn 边界捕获 panic 后仍走 `finish_load_error`，其中 `core.error = Some(...)` 会拦住后续 `drive`（load.rs:63 `core.error.is_some() → return`）——崩溃 fiber 不会被 epoch 扫描反复扰动，只能经 restart 复位，与既有 Failed 语义一致。

## 5. panic profile 钉死（四题）

1. **显式钉死**：Cargo.toml `[profile.release]` 增 `panic = "unwind"`，行注释写明原因（panic 边界依赖 unwind 捕获；abort＝隔离全失效且 Fatal 优雅退出也无机会执行）。`[profile.dev]` 同步显式写 `panic = "unwind"`（默认虽是 unwind，显式化防误改；test/bench profile 继承）。
2. **编译期硬门（主防线）**：`crates/yunyou/src/lib.rs` 顶部加：
   ```rust
   #[cfg(panic = "abort")]
   compile_error!("yunyou 内核必须以 unwind 编译：panic 边界（工具/装卸/事件监听）依赖 unwind 捕获，abort 使全部隔离机制失效");
   ```
   该 cfg 对所有 profile 生效——任何人任何方式改 abort，构建立即失败，**不依赖 CI 是否在跑、不依赖人的自觉**。
3. **CI 辅查（第二道）**：CI workflow 建立时纳入两步：`grep -n 'panic' Cargo.toml` 断言 unwind 行存在；`cargo build --release` 过硬门。CI 尚未建立，此条记入建 CI 时的清单（先行的硬门已兜底）。

## 6. 毒化注入测试三件套（五题：直接进验收）

落点：`crates/yunyou/tests/crash_isolation.rs`（新文件，风格对齐既有 tests/lifecycle.rs；工具用内核公开 API 手写 mock 插件，不引 mock 框架）。

### 6.1 三件套用例

1. **持锁 panic 注入**：
   - `毒化插件甲`：setup 内调用 `ctx.effect("毒化", |_| -> Result<Option<Disposer>> { panic!("毒化注入") })`——插件闭包经 `FiberShared::effect` 在决策锁内同步执行（effect.rs:101-116，凶点二源头）。**注**：`provide` 的注册体是内核闭包（service.rs:146-165），插件代码进不去；插件代码持锁执行的真实公开入口是 `ctx.effect`（附录 A 骨架细化时实测修正）。
   - `毒化插件乙`：setup 注册 `on` 监听器，监听器内 panic（覆盖事件面）。
   - `毒化插件丙`：setup 自身 panic（覆盖 run_load await 路径，凶点一）。
2. **断言（每例同构）**：
   - 主板存活：root fiber 仍 Active；root 上注册第二个**健康插件**其服务 `get` 成功、其工具经 `execute_tool` 正常往返；
   - 锁可用：对崩溃 fiber 与全局表的操作（`notify_services` 路径、状态读取）正常返回，不再 expect 连环炸（parking_lot 生效）；
   - 状态未破坏：崩溃插件 `state() == Failed`（**显式断言非 Loading——幽灵态回归断言**，凶点一的直接验收）；status 事件序列含 `failed`；
   - 卸载流程触发：若毒化插件曾 provide 服务且健康插件 inject 了它——健康插件随后收到「依赖未就绪」转 Pending 的完整链条（epoch 重算→卸载→Pending），断言状态事件序列；
   - panic 归一：错误 kind = `PluginPanicked`，payload 含 panic 信息。
3. **不击穿（同锁隔离）**：健康插件与毒化插件共存于同一服务表（inject 同一上游服务、共享全局表），毒化插件崩溃后：健康插件正常装卸（toggle enable/disable 往返）、其监听器正常收到事件、waterfall 链正常走完——证明扫描总线/监听表/waterfall 未被击穿。

### 6.2 插拔 N 次内存不涨

- **主断言（CI 确定性）**：循环 N 次（N≥50）：restart 崩溃插件（每次进 Failed）＋健康插件 toggle 往返——收尾断言 Arc 强引用计数回落至基线（对齐 lifecycle 既有强计数断言风格），fiber 表弱引用数量不涨。
- **辅断言（手动档）**：`#[ignore]` 用例循环 N=1000 次插拔，采样 `/proc/self/status` VmRSS，允许常量级抖动、不允许线性增长。定档理由：RSS 受分配器影响波动大，不宜作 CI 主断言；强计数是内存不涨的因果直接证据。

### 6.3 工具面补测

毒工具 `execute` 内 panic → 断言返回 `tool/panic` 错误、对话轮（agent-loop 消费侧）不崩——executor.rs 已实现但无专项测试（grep 确认），本轮补上。

## 7. v2 子进程隔离：四坑预留接口位（六题；实现留二期 S9，本文只定接口形状）

统一抽象见 §8。SubprocessRunner 的四坑与预留位：

| # | 坑 | 预留接口位（一期只占位不实现） |
| --- | --- | --- |
| 1 | 孤儿进程收割 | `RunnerHost::spawn` 返回 `ChildGuard`：内部 Linux `prctl(PR_SET_PDEATHSIG)`（子进程预设）＋ `killpg` 进程组强杀＋ Drop 兜底收割（waitpid 不悬挂）。父进程死亡时 OS 侧先杀一层，Drop 杀第二层 |
| 2 | stderr 独立消费防管道死锁 | `SubprocessSpec { stderr_policy: Pipe | Discard | File(PathBuf) }`；Runner 内建**独立 drain 任务**常驻读 stderr（OS 管道缓冲约 64KB，不读满则子进程写阻塞假死）→ 环形缓冲供诊断取用。stdout 走 RPC 帧，stderr 与协议流分离 |
| 3 | RPC 心跳＋每请求超时＝软崩溃计入熔断 | `RunnerHealth { heartbeat_interval, request_timeout, circuit: CircuitPolicy }`；`CircuitPolicy { failure_threshold, cooldown }`——单请求超时记一次软崩溃（区别于进程死亡=硬崩溃），阈值触发熔断→强制重启子进程。心跳复用 JSON-RPC ping 帧 |
| 4 | 熔断后资源强制回收 | `ResourceLedger`：子进程启动握手时上报资源清单（监听端口/临时目录/文件锁归属），熔断回收=杀进程组（坑 1）＋按清单强制清理（tmp 根目录整删＋端口属主已死自然释放＋锁文件删除）。临时资源强制约定落在 host 指定 tmp 根下，禁写他处 |

**与 §3 边界的关系**：SubprocessRunner 下 `is_panic`/`tool/panic` 的位置换成 RPC 层错误（超时/断连/协议错），归一错误码与熔断计数对齐坑 3——内核侧错误面不变，这是抽象成立的关键。

## 8. PluginRunner 统一抽象（七题）

### 8.1 与既有 Plugin trait 的关系（正交，不并发组件契约）

- `Plugin` trait（registry.rs:25-63）=**组件契约**：name/inject/manifest/setup——「插件是什么、依赖什么、怎么装」。**不动**。
- `PluginRunner` =**隔离策略**：「契约方法在哪里、以什么方式执行」——InProcessRunner=同进程（内核任务 spawn 边界直调，即 §3 方案的产品化）；SubprocessRunner=子进程 RPC（S9）。同一份组件契约，两种隔离强度，插件作者无感。
- **不引 async_trait**：沿仓库 BoxFut 惯用法（与 `Plugin::setup`、`Tool::execute` 同款，yunyou-util/lib.rs:21），trait 方法返回 `BoxFut<'static, _>`。

### 8.2 trait 草案（接口位，一期落 InProcessRunner，签名终审留 S9）

```rust
/// 隔离策略层：内核经此调用插件，不感知执行形态（同进程/子进程）。
pub trait PluginRunner: Send + Sync + 'static {
    /// 装载：执行插件 setup。InProcess = 内核任务 spawn 边界 + panic 归一（§3/§4）；
    /// Subprocess = 起进程 + RPC 握手（S9）。失败（含 panic）一律归一为 CordisError。
    fn load(&self, spec: LoadSpec) -> BoxFut<'static, Result<FiberOutput>>;
    // S9 预留位（先注释占位，不进一期签名，防过早固化）：
    // fn call_tool(...) -> BoxFut<'static, ToolOutcome>;   // 工具面：InProcess 转发 execute_tool
    // fn health(&self) -> BoxFut<'static, RunnerHealth>;   // 坑 3 心跳/熔断面
    // fn teardown(&self, ledger: ResourceLedger);          // 坑 4 强制回收
}
```

- `LoadSpec { plugin: Arc<dyn Plugin>, ctx: Context, config: ConfigValue }`（一期）；S9 时 `LoadSpec` 增补子进程形态字段（manifest 路径/Runner 配置），字段级扩展不破坏 trait。
- **load.rs 的依赖方向**：`run_load` 依赖 `Arc<dyn PluginRunner>`（root 持有，默认 InProcessRunner），不再直调 `plugin.setup(...).await`——panic 边界收进 InProcessRunner 内部，内核装卸逻辑只认 `Err`。
- 工具面一期不动（`execute_tool` 已是统一入口且带边界）；S9 时把 `call_tool` 纳入 trait，agent-loop 经 Runner 调工具——**这也是 §7 四坑的实现挂点**。

### A.4 实现注意（写进 S-ISO-4 任务卡验收备注）

1. **注入 panic 不污染测试进程**：C1/C5/C7/C9 的 panic 均发生在 tokio 任务或被 `catch_panic` 收敛处，测试进程本体不 panic；断言「预期 panic 已被边界捕获」，与「测试自身崩溃」严格区分。
2. **runtime 形态**：`#[tokio::test]` 默认当前线程 runtime（低 flaky）；C3 扫描用例如需多线程覆盖，单独标 `flavor = "multi_thread"` 并只做状态断言。
3. **C6 语义裁决先行**：waterfall panic 后「监听器所在环 Err 短路 vs 链继续」需 S-ISO-2 实现前由云枢终审（涉及 `internal/update` 重启语义），用例不得在裁决前定稿。
4. **C12 基线采样点**：装载前采一次、循环后 `wait_state` 全部稳定再采，避免在途任务持有计数造成假阳性。
