## 1. 总纲：三层装配模型

### 1.1 三层定义与组件映射

```text
┌──────────────────────────────────────────────┐
│ 编排层（可选，仅大 agent 进程加载）             │
│ 任务图管理 / 花名册管理 / 审核 / 清账 / 面板API │
├──────────────────────────────────────────────┤
│ 扩展层（可选，按 worker 角色启用）              │
│ 人设注入 / 会话隔离 / 成本记账 / 通知           │
├──────────────────────────────────────────────┤
│ 核心层（永远在，最小）＝修复型 worker 的全部     │
│ 读写 / 沙箱 / 模型调用 / 日志 / 循环            │
└──────────────────────────────────────────────┘
```

| 层 | 能力项 | 承载组件（对标内核方案已过审设计） |
| --- | --- | --- |
| 核心 | 循环 | yunyou（fiber 状态机）+ yunyou-agent-loop |
| 核心 | 模型调用 | yunyou-llm（契约）+ yunyou-llm-openai（Provider） |
| 核心 | 读写 | yunyou-tools 内置工具的 read/write/glob/grep 子集 |
| 核心 | 沙箱 | yunyou-tools 执行器（路径约束/超时/进程组收割）+ yunyou-procmgr std 核心 |
| 核心 | 日志 | yunyou logger + 结构化 Message/Exporter |
| 扩展 | 人设注入 | persona 组件：persona_ref 文件 → systemPrompt 配置，经内核 **intercept 链合并**（内核方案 §2.2），无代码特判 |
| 扩展 | 会话隔离 | session-isolation 组件：按 worker 声明独立 session_dir + 会话事件与 task_id 关联 |
| 扩展 | 成本记账 | cost-meter 组件：采集 token/耗时/工具调用次数，随 submit 经 WorkerDao 上报 |
| 扩展 | 通知 | notify 组件：一期写任务事件日志，预留 webhook trait（crate 模块，接口先行） |
| 编排 | 任务图管理 | team-orchestrator 内 taskgraph-service：拆任务/派活/sweeper |
| 编排 | 花名册管理 | roster-service：worker_registry 表的注册/暂停/退役维护 |
| 编排 | 审核 | review 组件：probe 先行的确定性验证 + 模型补充审核 |
| 编排 | 清账 | accounts 组件：任务账/成本账/能力账三层（二期落能力账表） |
| 编排 | 面板 API | admin 组件：消费 admin_commands 表（§5.5） |

### 1.2 层 → crate / feature / 二进制产物映射（验收项②）

**裁决：以「crate 边界 = 层边界」为铁律，禁止用一个 crate 内 feature 组合表达层边界**（裁决理由与代价对比见 §1.3）。

| 二进制产物 | 装配 = 依赖闭包 | 所属 crate |
| --- | --- | --- |
| `yunyou-worker-core`（＝修复型 worker） | 核心层：yunyou + agent-loop + llm(-openai) + tools(核心面) + procmgr(std) + taskgraph（**仅 worker_dao/ddl/lease**，见 §4.1）+ 行为固定提示词（编译期常量） | `team-worker-core` |
| `yunyou-worker`（＝员工型 worker） | 核心层（同上，经依赖 team-worker-core）+ 扩展层 team-worker-ext（按 capabilities 装配） | `team-worker` |
| `yunyou-cli`（＝大 agent） | 内核方案全套组件 + 编排层 team-orchestrator | `yunyou-cli`（既有）+ `team-orchestrator` |
| `yunyou-launcher` | 无层属性：procmgr(std) + util 级类型 + 错误包 schema 类型 | `team-launcher` |
| `yunyou-probe` | 无层属性：util 级类型 + 探针检查 | `team-probe` |
| `yunyou-panel`（一期只读） | 无层属性：只读 SQLite 副本 + 文件系统 | `team-panel`（二期） |

- 扩展层「按 worker 角色启用」的语义：**装配门控而非代码门控**——`yunyou-worker` 产物含扩展层代码（合法，蓝图七-1 只约束修复产物），运行时按花名册 capabilities 条件 `ctx.plugin`（如无 persona_ref 不挂 persona 组件）。
- feature 的唯一用途：**非安全边界的运行时适配**，如 yunyou-procmgr 的 `"tokio"` feature（异步适配层）——不承载层边界（§1.3 裁决）。

### 1.3 分层装配机制裁决（验收项②的机制部分）

| 候选机制 | 是否满足「编译产物里就没有」（补注一强化措辞） | 代价 | 裁决 |
| --- | --- | --- | --- |
| A. cargo features 物理裁剪 | 仅当构建修复产物时 `--no-default-features` 且全部越层依赖 optional 才成立；默认 feature 全开即产出「全能力」二进制，纪律一旦失守静默破坏七-1 | ① feature additive 陷阱：组合矩阵 2^n，CI 须逐组合跑 `cargo tree` 验证，脆弱且易漏；② cfg 散落各模块，可读性差；③ optional 依赖的传递性易把越层代码悄悄拉回 | **否决**（仅保留 procmgr tokio 等非安全适配用途） |
| B. 多二进制（分层 crate，每 bin 一个装配清单） | **编译事实级满足**：`yunyou-worker-core` 的 Cargo.toml 不声明扩展层/编排层依赖 → cargo 解析的依赖闭包物理不含其代码；`cargo tree -p team-worker-core` 可机器验证 | ① crate/bin 数 +2；② 共享类型须下沉（taskgraph DAO、schema 类型独立成库）；③ 每 bin 薄装配清单约 50 行的少量重复 | **采纳为主** |
| C. 纯配置门控（运行时 if/flag） | 不满足：代码在产物里，只是运行时不激活 | 无 | **排除**（直接违反蓝图七-1「不是配置关掉」） |

**门禁落地**（并入内核方案 §2.9 的 xtask deps-gate，任务 2 验收项同批实现）：
`cargo xtask deps-gate --bin yunyou-worker-core` 解析该 bin 依赖闭包，命中黑名单（team-worker-ext / team-orchestrator / persona 加载）即失败；`yunyou-launcher`、`yunyou-probe` 的闭包另禁 yunyou 及一切 team crate（内核方案 §2.7.2 边界的机器化）。crate 边界=层边界零例外（§4.1），门禁规则统一按 crate 依赖列表，无专属例外规则。CI 与本地 pre-push 同跑。

### 1.4 与内核方案 §2.7.2 边界一致性

内核方案 §2.7.2 表（launcher/修复 worker/探针不依赖内核；大 agent 与员工 worker 复用内核）在本方案中的对应升级：修复 worker 从「不依赖内核」精确为「**依赖核心层**」——核心层本身含 yunyou/agent-loop/llm/tools（业主补注一明示核心层是循环+模型调用，即修复 worker 仍是一个最小 agent，与蓝图二-4「行为固定」不矛盾：行为固定=提示词编译期常量+工具面最小）。其余角色边界不变；不一致处本节已声明，无暗改。

## 2. 核心层：`team-worker-core` 与修复型 worker

### 2.1 装配清单（yunyou-worker-core 二进制）

- yunyou root Context → 依序 plugin：llm(openai 兼容，可配 DeepSeek) → tools（**工具面锁死为 read/write/glob/grep**，路径约束见 §2.3）→ agent-loop。
- **行为固定**：系统提示词为编译期常量（`PROMPT: &str`），不接受任何外部人设/角色输入；agent-loop 的 Config 走内置默认，不读花名册。
- 会话记录落错误包指定隔离目录（核心层日志语义，无独立 sessions 组件——蓝图二-4 修复 worker 一次性运行，最小记录即可）。

### 2.2 修复 worker 运行边界

- 输入：仅 `--error-package <dir>`（错误包，§5.2）与 `--out-dir <隔离区>`；**clap 子命令不存在 `--persona`/`--taskgraph`/`--roster` 参数**（蓝图七-1/九）。
- 产出仅两种安全结果（蓝图五-2）：`disable: [...]` 禁用标记，或隔离副本内候选补丁 + ed25519 签名元数据（§3.4）；生产 profile **只读**（代码中不存在写句柄构造）。
- 权限最小化（蓝图七-8）：只读错误包、只写隔离区、只跑验证探针；超时由 launcher 侧 procmgr 强杀（§8）。

### 2.3 沙箱语义（核心层「沙箱」项的落地）

工具执行器（内核方案 §2.5 yunyou-tools executor）对核心层装配强制：工作目录锚定（修复=错误包目录+隔离区；员工=任务 workspace）、路径白名单外拒绝、单工具超时、进程组收割（procmgr）、输出尾部截断。执行器契约沿用内核方案对 dsh `contracts.ts:30-46` 的对标设计（exec.signal 取消传播）。

## 3. 扩展层：`team-worker-ext` 与员工型 worker

### 3.1 crate 结构（一个 crate 四模块，每模块一个扩展插件）

`crates/team/team-worker-ext/src/{persona.rs, session_isolation.rs, cost_meter.rs, notify.rs}`——四组件同为内核插件（`impl Plugin`），装配清单在 `yunyou-worker` bin：按花名册 capabilities 条件挂载（无对应 capability 不 plugin，不占 fiber）。四组件合一个 crate 的理由：均为小型装配面组件（各 ≤150 行），合 crate 避免 crate 数爆炸；模块间无依赖，后续任一组件长大可独立成 crate（预留）。

### 3.2 双模式启动参数与配置来源物理隔离（蓝图三末段/验收项③）

| | `yunyou-worker --mode team` | `yunyou-worker-core`（修复） |
| --- | --- | --- |
| 参数 | `--taskgraph <db> --persona <file> --worker-id <id> [--session-dir <dir>]` | `--error-package <dir> --out-dir <dir> --timeout <ms> --keyring <pub>` |
| 人设 | persona 组件读 persona_ref 花名册文件 → intercept 链 | **产物中无人设代码**（依赖闭包不含 persona 模块） |
| 配置来源 | 任务图 + 花名册 + capabilities | 错误包 + 受控候选区（签名验证） |
| 任务图访问 | WorkerDao（§4.2） | **产物中无任务图代码**（不含 team-taskgraph 依赖） |

### 3.3 扩展组件要点

- **persona**：解析人设文件（schema 见 §7）→ 转为 systemPrompt 组件 Config 片段 → `ctx.intercept("systemPrompt", …)` 合并；人设版本记入花名册 persona_version，变更即生效于下次领取的任务。
- **session-isolation**：为本次任务声明独立 session_dir（任务图 workspace 旁），sessions 组件的存储路径按其配置重定向；会话事件首条写 task_id 关联（可追溯，面板可跳转）。
- **cost-meter**：包装 llm/tools 调用计数（token 由 llm 组件用量回调、耗时与工具次数由执行器回调），submit 时经 WorkerDao 一并上报；配额超限上报 `cost_quota_exceeded` 事件，由编排层决定熔断（扩展层不熔断——单一职责）。
- **notify**：一期实现 = 任务事件结构化日志（接 cordis logger exporter）；预留 `NotifySink` trait（webhook 等后接），不承诺一期外发。

## 4. 编排层：taskgraph / orchestrator / 花名册 / 审核 / 清账 / 面板 API

### 4.1 编排逻辑整体归属 team-orchestrator（返修一：crate 边界零例外）

**裁决（2026-11-13 评审返修一定稿）**：任务图的**编排逻辑全部迁入编排层 crate**，team-taskgraph 保持纯存储形态，「crate 边界=层边界」零例外：

- `team-taskgraph`（核心层可依赖）：`ddl.rs`（三表建库与迁移）、`worker_dao.rs`（claim/heartbeat/submit/report_cost 四个原子操作，纯 SQL 封装，无状态流转决策）、`lease.rs`（租约计算与过期判定纯函数）——这是 worker 的领取通道，不是编排逻辑；
- `team-orchestrator`（编排层，仅 `yunyou-cli` 链接）：`reviewer_dao.rs`（状态流转唯一写方）、`review.rs`（审核）、`accounts.rs`（清账）、`taskgraph_service.rs`（拆任务/派活/sweeper）、`admin.rs`（admin_commands 消费）。reviewer 依赖 team-taskgraph 的表类型与连接 = **编排层向下依赖核心层 crate，方向合法**（与 orchestrator 依赖 yunyou 同向）。

deps-gate 因此无需任何专属例外规则：worker 产物依赖闭包含 team-taskgraph（合法，无编排符号——符号只存在于 team-orchestrator）而不含 team-orchestrator（黑名单）。

### 4.2 DDL（SQLite 3.44+，WAL，单文件 `<yunyou-home>/team/tasks.db`）

```sql
PRAGMA journal_mode = WAL;
PRAGMA busy_timeout = 5000;
PRAGMA foreign_keys = ON;

CREATE TABLE schema_meta (           -- 对标 dsh「SQLite 单调 SCHEMA_VERSION」纪律
  version INTEGER NOT NULL           -- 迁移只增不改；已发布代际不移动不覆盖不删除
);

CREATE TABLE tasks (
  task_id      TEXT PRIMARY KEY,                 -- ULID
  parent_id    TEXT REFERENCES tasks(task_id),   -- 子任务
  status       TEXT NOT NULL CHECK (status IN
               ('pending','claimed','running','submitted','approved','rejected','blocked')),
  claimed_by   TEXT,                             -- worker_id
  claimed_at   INTEGER,                          -- unix ms
  lease_until  INTEGER,                          -- unix ms；防 worker 崩溃卡死（蓝图四-1）
  workspace    TEXT NOT NULL,                    -- 独立工作区绝对路径
  session_dir  TEXT NOT NULL,                    -- 独立会话目录绝对路径
  input        TEXT NOT NULL,                    -- 任务描述/上下文（JSON，schema §7）
  output       TEXT,                             -- 提交物路径（worker 提交时写）
  review_notes TEXT,                             -- 仅审核方写
  attempts     INTEGER NOT NULL DEFAULT 0,
  cost_tokens  INTEGER NOT NULL DEFAULT 0,       -- 蓝图 cost 拆三列，聚合查询友好
  cost_ms      INTEGER NOT NULL DEFAULT 0,
  cost_tool_calls INTEGER NOT NULL DEFAULT 0,
  priority     INTEGER NOT NULL DEFAULT 0,
  updated_at   INTEGER NOT NULL
);
CREATE INDEX idx_tasks_claim ON tasks(status, priority DESC);

CREATE TABLE worker_registry (       -- 花名册/能力注册表（蓝图四-2）
  worker_id     TEXT PRIMARY KEY,
  role          TEXT NOT NULL,
  persona_ref   TEXT,                           -- 人设文件路径；仅员工型有值
  persona_version TEXT,
  capabilities  TEXT NOT NULL,                  -- JSON array，如 ["rust","testing"]
  max_concurrency INTEGER NOT NULL DEFAULT 1,
  cost_quota    INTEGER,
  status        TEXT NOT NULL CHECK (status IN ('active','paused','retired')),
  updated_at    INTEGER NOT NULL
);

CREATE TABLE admin_commands (        -- 面板有限写操作落点（§5.5）
  cmd_id     TEXT PRIMARY KEY,
  kind       TEXT NOT NULL CHECK (kind IN ('pause_task','release_lease','escalate_human','trigger_agent_update')),
  payload    TEXT NOT NULL,                    -- JSON，schema §7
  status     TEXT NOT NULL CHECK (status IN ('queued','applied','rejected')),
  created_by TEXT NOT NULL DEFAULT 'panel',
  created_at INTEGER NOT NULL,
  applied_at INTEGER
);
```

### 4.3 租约语义与过期回收（蓝图七-3）

```sql
-- 同一事务两步：
UPDATE tasks SET status='pending', claimed_by=NULL, lease_until=NULL
 WHERE status IN ('claimed','running') AND lease_until < :now;        -- ① 惰性回收过期租约
UPDATE tasks SET status='claimed', claimed_by=:wid, claimed_at=:now,
       lease_until=:now + :ttl, attempts=attempts+1
 WHERE task_id = (SELECT task_id FROM tasks
                  WHERE status='pending' ORDER BY priority DESC, task_id LIMIT 1)
   AND status='pending';                                              -- ② 原子领取（蓝图四-1 原文）
```

- **心跳续租**：worker 每 `ttl/3` 执行 `UPDATE … SET lease_until=:now+:ttl WHERE task_id=:tid AND claimed_by=:wid AND status IN ('claimed','running')`；连续两次失败即弃任务（等①回收）。
- TTL 默认 10 分钟，任务可在 input 声明更长（上限由编排层审核）。
- **兜底 sweeper**（编排层 team-orchestrator 内组件）：30s 周期跑①，仅为面板可见性兜底，正常路径①已在每次领取前执行。
- **权限模型（蓝图七-2 类型化）**：SQLite 无列级权限 → **依赖闭包即权限**：状态流转写方 ReviewerDao 物理位于 team-orchestrator（§4.1），worker 产物（yunyou-worker / yunyou-worker-core）依赖闭包不含该 crate，approved/rejected/blocked 写路径在产物中不存在；集成测试断言 WorkerDao 无 approved 写路径。rejected ≥ N（默认 3，可配）→ blocked（蓝图五-1/七-7，冻结后无自动解禁路径）。
- **提交与清账**：worker `submit(task_id, output_path, cost)` 单事务写 output + cost 三列 + status='submitted'；清账三层（蓝图五-1）由编排层 accounts 组件执行——任务账（approved 终态）/成本账（按 worker×日聚合，供配额熔断）/能力账（`ability_ledger` 表二期落，一期预留字段）。

### 4.4 team-orchestrator：编排层插件集挂 Context（验收项④）

```rust
// crates/team/team-orchestrator/src/service.rs（签名级）
impl Plugin for OrchestratorService {
    fn name(&self) -> &str { "orchestrator" }
    fn inject(&self) -> Vec<ServiceKey> { vec![agentLoop, sessions, taskgraph, roster] }
    // setup 内：provide("orchestrator")；审核队列监听 fiber；admin_commands 消费 fiber
}
```

- **复用 fiber/effect**（内核方案 §2.1.4/§2.5）：`ctx.on(submitted)` 审核监听随 fiber 卸载自动清理；员工 worker 进程监督 = fiber effect 持 CancellationToken（orchestrator 卸载即收割全部子进程）；花名册注册 = effect（disposer 自动出册）。
- **「大 agent 不亲自干重活」（蓝图二-2）机制化**：挂载时 `ToolsService.restrict({ deny: [bash, write, edit, …] })` 收紧编排者工具面，只留任务图读写、探针调用、评审对话（对标 dsh tools/src/index.ts restrict 契约，内核方案 §1.9）。
- **审核优先确定性验证（蓝图七-4）**：submitted → spawn `yunyou-probe`（§6）→ probe 失败直接 rejected（不耗模型审核）→ 通过才进入模型补充审核（一次 agent-loop 评审对话）→ approved/rejected + review_notes。
- **小 agent 维护通道（蓝图五-3，二期）**：候选更新写 `candidates/` → 历史错误包演练自检 → 通过升 current（旧 current 转 lkg）→ 连续自检失败停止自动更新并告警；更新内容限定「数据 + 受限配置 + 经构建验证的二进制」；**lkg 目录代码中无删除接口**（蓝图七-6），清理走人工文档。

## 5. team-launcher：启动、错误包、救援态、降级链

### 5.1 启动流程（返修二：就绪探针语义，不以退出码判定成功）

**spec 修正**（评审指出）：正常运行的大 agent 不会退出，「exit==0 即成功」不成立——启动窗口内干净退出同样是失败。改为**就绪探针语义**：

```text
yunyou-launcher --profile <path> [--roster <path>]
 └─ 1. 预清理：删除残留就绪标记（防上次崩溃的 stale 文件误判）
 └─ 2. spawn yunyou-cli（procmgr std 核心：超时/退出码/stderr 尾部捕获）
 └─ 3. 启动窗口（--boot-window，默认 30s，可配）内轮询就绪标记：
      就绪标记 = <yunyou-home>/state/ready-<pid> 文件（yunyou-cli 装配完成后创建、
      优雅退出前删除——任务 3 yunyou-cli 的装配清单项，见 §9.2）
      ├─ 窗口内就绪 → 团队态：读花名册 → 按 max_concurrency×capabilities
      │    spawn yunyou-worker（人设经 --persona 注入）→ 落盘 team-state.json
      │    → launcher 退出（蓝图二-1）；worker 独立运行靠租约+面板观察
      ├─ 窗口内退出（无论退出码，含 exit==0）→ 救援态（§5.3）
      └─ 窗口耗尽仍未就绪 → kill + 救援态
```

选型说明：就绪标记选**文件**而非 stdout 就绪行（需解析协议、缓冲边界易错）或 probe smoke 调用（成本高，修复期不该跑真对话）；文件存在性轮询 procmgr std 核心即可完成，且 stale 残留用启动前预清理兜底（第 1 步）。

### 5.2 错误包格式（蓝图四-3 全字段，落 `<yunyou-home>/errors/<utc-ts>-<attempt>/`）

| 文件 | 内容 |
| --- | --- |
| `error-package.json` | 启动命令与参数、退出码/是否超时、**是否曾达就绪（ready 标记是否出现过）与就绪耗时**、stdout/stderr 尾部行数指针、profile 路径与配置快照、已装插件清单及版本、最近一次成功启动的插件清单（`yunyou-home/state/last-good-plugins.json`，无则 null）、隔离目录路径、launcher 版本与时间戳 |
| `stderr.tail.log` / `stdout.tail.log` | 最近 N 行（默认 2000，可配） |
| `profile.snapshot.toml` | 触发启动的配置快照（救援输入，不改原文件） |

### 5.3 救援态流程（蓝图五-2）

```text
生成错误包（含就绪探针结果，§5.1/§5.2）→ spawn yunyou-worker-core --error-package <dir> --timeout 10m（current 版本）
  ├─ exit==0 且 result.json 可解析 → launcher 校验：
  │    ├─ 禁用标记 → 合入 profile 隔离副本 → 重试大 agent
  │    └─ 候选补丁 → 隔离副本 spawn yunyou-probe 验证 → 通过才合入 → 重试大 agent
  ├─ current 失败/超时/崩溃 → 回退 lkg 重试一次（蓝图六）
  └─ lkg 也失败 → 四级降级链
```

### 5.4 四级降级链（蓝图六，fallback 顺序即实现顺序）

| 级 | 动作（launcher 独立执行，不依赖修复 worker） | 成功后 |
| --- | --- | --- |
| 1 | 禁用所有非核心插件（profile 禁用列表除内核白名单），安全模式启动 | 安全模式运行 + 告警 + 等人 |
| 2 | 已知可用最小 profile（`yunyou-home/profiles/minimal.toml` 随版本发布）启动 | 最小模式运行 + 等人 |
| 3 | 打印错误包路径 + 启动命令 + 退出码 + 最近日志 + 人工指引，**非零退出** | 交外部监督（systemd）或人工 |

每级尝试结果（含 spawn 失败）追加写错误包目录 `fallback.log`。

### 5.5 面板写操作落点（业主已裁决，蓝图补注二定稿）

**业主裁决（2026-11-13 03:00，蓝图补注二）**：面板有限写操作（暂停任务/释放租约/blocked 转人工/触发小 agent 更新）落任务图 `admin_commands` 表，由大 agent 进程内编排层 admin 组件异步消费执行。蓝图意图不变：面板始终是观察面，不直接控制任何进程；控制面 = 任务图 + 执行者；原文「launcher 接口」按补注二修订理解——admin 组件即 launcher 控制接口的异步形态；救援态无面板，维持原文。本方案 §4.1/§4.4 的 admin 组件设计即该裁决的落地。

## 6. team-probe：验证探针检查项清单

独立二进制（无层属性），单次调用单类检查，输出结构化 JSON（schema §7）：

## 8. 进程管理共享底座（yunyou-procmgr）

`crates/yunyou-procmgr`（内核方案 §2.7.2 末段预告，避免 launcher 与阶段 3 插件协议各写一份）：

- **std 同步核心**（无 tokio；launcher/修复 worker/probe 可用）：spawn（命令+参数+工作目录+env 约束）、wait_timeout（超时 kill 进程组）、退出码、输出尾部滚动捕获（环形缓冲）、kill_on_drop 收割防僵尸、重试预算（次数+退避）。
- **tokio 适配层**（feature `"tokio"`，内核阶段 3 用）：异步 spawn/输出流/取消联动 CancellationToken。feature 仅做运行时适配、不承载层边界（§1.3）。
- procmgr 只管单进程生命周期；组监督由任务图租约承担（§4.3），不引入第二监督者。蓝图八「launcher 内超时+退出码检查；外层 systemd 兜底」照此分工。
- 纪律：procmgr 不解析业务语义；单源码文件 ≤300 行。

## 11. 风险点（云枢自标）

> 原风险 1（面板写操作调和）已注销：业主 2026-11-13 03:00 定稿 admin_commands 方案（蓝图补注二，§5.5）；原风险 4（taskgraph feature 例外口）已消除：评审返修一后 crate 边界=层边界零例外（§4.1）。

1. **DAO 依赖闭包即权限的强度有限（中）**：SQLite 无列级权限，ReviewerDao 与 WorkerDao 的隔离靠「编排逻辑物理在 team-orchestrator、worker 产物闭包不含之」（§4.1/§4.3）+ 测试，非数据库强制。一期威胁模型限定「worker 二进制由本仓库构建」+ deps-gate 断依赖；若未来出现第三方直连任务图，需升级「worker 专用 SQLite 账号 + 触发器」或独立网关进程。文档须写明该边界。
2. **worker 孤儿进程运维面（中）**：团队态 launcher 退出后 worker 独立运行（设计如此），异常退出靠租约回收 + 面板发现；「面板也挂且 worker 全崩」无自动兜底——蓝图定义为「等人」（降级 3 同理），方案不越权加自动重启；运维文档必须写清 systemd 只监督 launcher，不得监督 worker（避免双监督打架）。
3. **就绪标记的假阳/假阴（低-中）**：§5.1 依赖 ready 文件判定团队态——崩溃残留靠启动前预清理（stale 假阳已堵）；残余风险是 yunyou-cli 「装配完成」与「真正可用」的间隙过窄或过宽（装配完但 LLM 配置错，就绪标记已落）。对策：就绪标记创建时机 = 装配完成且首个健康自检（配置解析）通过之后，不要求真对话；错误包记录就绪耗时供修复 worker 判别（§5.2）。
4. **错误包体积失控（低）**：stdout/stderr 全量落盘可能巨大；默认尾部 2000 行 + 行数指针 + 完整落盘可选项，可配。
5. **阶段时序（低）**：taskgraph 纯存储不依赖内核，阶段 A 可与任务 2 并行；阶段 B 依赖任务 2+3，若任务 2 返工仅顺延阶段 B，阶段 A 不受影响——拆解已解耦。
