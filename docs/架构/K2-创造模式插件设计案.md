# K-2 创造模式插件设计案（池 task-11，设计先行不动码）

> 承办：云点｜性质：设计报裁（lead 裁后实施，实施候 68 MVP+本设计双前置）｜日期 2026-11-17
> 基座：L2 外部装载缝设计-K19（已批）+装载器最小方案（L1 实测）+K-3 官方规范（dsh-plugin-dev 契约面）+插件交付规则（业主定）。

## 一、目标与 MVP 边界

**创造模式**=业主在会话内让云悠协助**从零做插件**：读契约→生成骨架→装载校验→交付产出。MVP 边界（诚实划线）：
- **L1 级全量**：manifest（v1 现格式+v2 字段骨架前向兼容）生成与校验（复用 L1 发现层 parse_manifest_toml+validate_manifest_static 现成函数，零新解析器）；
- **L2 级占位**：v2 字段（format/runtime/permissions）按 K-19 §3.1 schema 校验，**运行时联调候 68 MVP**（校验=静态/schema 级，不 spawn 插件进程）；
- **不做**：凭据面插件（红线继承）、WASM、market 分发上传。

## 二、工具集（四件，走 tools.v1 契约注册缝）

| 工具 | 职责 | 参数 | 写边界 |
|---|---|---|---|
| `plugin_contract_read` | 契约面速查：manifest 字段表（v1 八字段+v2 新增段）+K-3 骨架模板+交付规则三件套清单——**只读内嵌契约包**（编译期 const，不读用户盘） | `topic`（manifest/skeleton/delivery） | 无写 |
| `plugin_scaffold` | 骨架生成：`<id>/manifest.toml`+入口文件+README 模板落盘 | `id`/`name`/`description`/`entry_lang`（python/node/bash）/`capabilities` | **限 `<yunyou-home>/plugins/<id>/`**（L1 发现目录=装即可被发现的正道；工具级 allowlist 闸，见 §四） |
| `plugin_validate` | 装载校验：parse+静态校验+v2 schema 检查+`[plugins.<id>]` 冲突预检，产出人话诊断清单（错误=逐条+修法，复用 L1 fail-loud 文案族） | `id` | 无写（纯读校验） |
| `plugin_deliver` | 交付打包：npm pack 等价（tar 白名单）→`<id>-<version>.tgz`+安装教程.md+介绍.md 三件套落 `<workspace>/dist/插件/<功能名>/` | `id`/`version` | 限 workspace dist 目录（resolve_workspace 闸内） |

**与 edit/write 的分工**：骨架生成用 scaffold（目录+模板一次成型+allowlist 语义）而非裸 write（写边界不同：plugins 目录在 workspace 外）；微调仍用 edit（scaffold 后的人肉迭代=既有工具链，不重复造）。

## 三、系统提示段（契约③ section 注册）

`creation_mode` 段（order 靠后，仅声明了创造意图的会话注入——§7 开放问题 2 候裁「按需注入 vs 常驻」）：

1. **manifest 先行**：先写 manifest.toml 过 validate，再写入口代码（契约即规格，防先码后补证）；
2. **fail-loud 循环**：validate 报错逐条修，禁「跳过校验先交付」；
3. **红线三条**：插件不得读凭据（L2-MVP 凭据面不开）；禁绝对路径与 `..` 上跳（K3 B-5 同构）；声明面与实现面一致（provide 了就必须有）；
4. **交付清单**：三件套齐+装后验证义务（安装后必须验证可用，不许只推不验——业主定）；
5. **授权话术**：装载（重启生效）与启用（/plugins 开关）动作**告知用户自行执行**，代理不代按。

## 四、安全边界（三闸+一红线）

1. **写闸（工具级 allowlist）**：scaffold/deliver 的写目标=白名单前缀硬校验（`<home>/plugins/<id>/` 与 `<workspace>/dist/插件/`），越界=tool/path-outside-root 人话拒——**不走 resolve_workspace**（plugins 目录在 home 下、workspace 外，两套闸并列不混用，52 单义文档加注）；
2. **授权闸（用户专属）**：装载/启用/交付推送三动作=用户执行或用户显式确认（agent 话术引导，不代执行）——「授权类动作只能留给用户」（K-19 §3.1 permissions.writable 同构原则）；
3. **校验闸（装前静态）**：v2 schema 全检（format/runtime/permissions 非法值拒）+开放面白名单（L2-MVP 仅 tools.v1，声明白名单外=拒装话术预演）——K-19 §3.1 校验列的**预演实现**（68 落地后同函数复用，防两处漂移=函数放 config/manifest_file 共享位）；
4. **红线继承**：凭据面不开（permissions.credentials 非空=校验即拒）、`role('secret')` 消费器语义不破、网络 MVP 恒拒。

## 五、依赖与序

```
68 MVP（L2 运行时+proto 落地）
   ↓ 提供：装载运行时（validate 的 runtime 联调级+真机 invoke）
K-2 实施（本设计四工具+提示段）
   ↓ 交付：创造模式闭环
业主真机（创造→装载→验证→交付全链）
```

实施拆卡建议：四工具各一卡（contract_read 最小先行/scaffold+validate 成对/deliver 随交付规则细则）+提示段一卡。

## 六、验收预案（实施后）

1. skeleton→validate 零错→重启→/plugins 可见（L1 自举链复验）；
2. v2 非法值（format=3/runtime.type=wasm/credentials 非空）→validate 逐条人话拒；
3. scaffold 越界写（id=../逃逸）→allowlist 拒；
4. deliver 三件套落位+安装教程路径与实际一致（交付规则验收条）；
5. 提示段注入/不注入两态（按需注入裁决后）。

## 七、开放问题（报裁）

1. **scaffold 落点**：`<home>/plugins/<id>/`（装即可见）vs `<workspace>/plugins-staging/<id>/`（工作区暂存，用户手动搬运）——建议前者（L1 发现即验证闭环，用户搬运=多余步）；
2. **提示段注入策略**：常驻 vs 按需（会话内出现创造意图关键词时注入）——建议常驻（段文本小，按需=意图识别新机制，MVP 不做）；
3. **deliver 的 adb push**：工具内做 vs 教程指引用户自做——建议教程指引（物理推送=业主设备动作，工具不碰 ADB）；
4. **v2 字段生成深度**：scaffold 生成 v1 现格式（L1 即验）还是 v2 全骨架（含 runtime/permissions 占位）——建议 v1+注释行 v2 预留（68 落地前 v2 校验无运行时对账，防纸面字段）。
