# 云悠（YunYou）组件内核架构方案（对标 Cordis）

> 作者：云枢（首席架构师）｜评审：云悠（待评审）｜日期：2026-11-13
> 依据：`/home/wu/agent/deepseek-harness/vendor/cordis/` 全量源码（8 个核心文件 + loader/hmr/include/group 配套）与 `packages/core/`、`packages/boot/` 实际用法。本文所有 TS 结论均给出 `文件:行号` 证据；路径均相对 `deepseek-harness/`。
> 业主既定决策：云悠（工程仓库代号 yunyou，与目录/crate 同名）的核心是 Rust 版组件内核——组件的装配、替换、生命周期由内核管理；agent-loop、LLM、工具、存储、CLI 一切皆内核上的组件。组件化 ≠ MCP：MCP 只是未来被插件系统集成的能力协议之一。

## 0. 结论速览

1. Cordis 的本质是「**原型链式的作用域 + 以函数为身份的插件注册表 + epoch 版本号驱动的装载/卸载状态机 + 一切注册皆 effect（可撤销）**」。这四件事全部可以用 Rust 平移，但**载体完全不同**：TS 靠运行时 Proxy 和原型链，Rust 靠显式 trait + `Arc`/`Weak` 引用图 + 类型键注册表。
2. TS 版的「动态」有两层：**组件实例级动态**（重装载、配置热更、服务替换——Rust 完全可平移）与**代码级动态**（npm 运行时装包、HMR 换模块——Rust 无此生态，必须换成「编译期注册 + 配置驱动装配 + 子进程/WASM 扩展」，见 §2.4 D3/D4）。
3. 内核 crate 定名 `yunyou`（品牌名「云悠」YunYou，业主 2026-11-13 定名；`yunyou` 为 crate 标识符），组件 crate 按 dsh 包一一对应（`yunyou-llm`、`yunyou-session`……），入口 `yunyou-cli`。单向依赖：cli → 组件 crates → yunyou；组件间运行时依赖一律走内核服务解析，不走 crate 直接依赖（类型除外）。
4. 异步运行时选 **tokio（多线程调度）**，理由见 §2.3。
5. 业主《小 Agent 团队架构》蓝图（`docs/需求/小Agent团队架构.md`）是内核之上的**多进程层**：内核只被「大 agent」与「员工型 worker」进程复用；launcher / 修复型 worker / 验证探针**不依赖内核**（依赖压到最低）；跨进程协作只走任务图（SQLite）与文件系统，不走内核事件总线。详见 §2.7.2。
6. 接口文档策略（task-1 第 9 项硬性要求）：对外 HTTP/WS/IPC 采用 **OpenAPI 3.1 + JSON Schema 2020-12** 双轨，以代码内 serde/utoipa 注解为唯一真源、生成物落盘 `docs/接口/` 并由门禁校验；内部组件接口用 rustdoc + trait 契约文档。详见 §2.8。

## 1. TS 版 Cordis 机制研读（源码证据）

### 1.1 总体结构：一个 Context 代理 + 四个内置服务

- `Context`（`vendor/cordis/src/context.ts:42`）在构造时创建 `isolate`（服务名→作用域标签映射，`context.ts:18`）与 `intercept`（服务名→配置拦截映射，`context.ts:20`）两张表，并安装四个内置服务：`reflect`（服务解析）、`registry`（插件注册）、`events`（事件总线）、`logger`（日志），最后 `return self`——self 是套了 `ReflectService.handler` 的 Proxy（`context.ts:71-84`）。
- 因此 TS 里 `ctx.foo` 的属性读取会进入 Proxy 拦截：未声明且未注入的服务直接抛 `cannot get property "foo" without inject`（`reflect.ts:152`），已声明的服务沿 **fiber 链向上**查找实现并按 `isolate` 标签匹配（`reflect.ts:163-180`）。
- 子上下文三件套（全部是「创建新对象、不改父」）：
  - `extend(meta)`：以 `Object.create(父)` 造子上下文，叠加自有属性（`context.ts:99-107`）——TS 原型链继承；
  - `isolate(name, label)`：为服务 `name` 换作用域标签，同标签 = 同作用域（`context.ts:121-125`）；
  - `intercept(name, config)`：给该子树下的插件往服务配置里合并一段拦截配置（`context.ts:139-145`）。

### 1.2 插件三形态与注册表

- 插件可以是函数、类、或 `{ apply }` 对象（`registry.ts:92-133`）；共享元数据：`name` / `Config`（StandardSchema 校验器）/ `inject`（依赖的服务）/ `provide`（提供的服务名）/ `intercept`（声明消费的拦截配置）（`registry.ts:100-111`）。
- `RegistryService._internal` 是 `Map<Function, Plugin.Runtime>`——**以插件函数本身为身份键**，同一函数多次 `ctx.plugin()` 共享一个 Runtime、各自得到一个 Fiber（`registry.ts:197,316-336`）。
- `ctx.plugin()` 返回的 Fiber 同时是 PromiseLike，`await` 即等到装载完成（含启动失败抛错）（`registry.ts:331-335`、`fiber.ts:754-760`）。
- `ctx.inject(deps, cb)` 是语法糖：`plugin({ inject, apply: cb })`，依赖变化时回调会被卸载重跑（`registry.ts:300-302`）。
- `@Inject` 装饰器：类上并入静态 `inject` 表；方法上把方法调用推迟到依赖可用（`registry.ts:37-60`）。

### 1.3 Fiber：生命周期状态机与 epoch 依赖追踪（内核的心脏）

- 状态机：`PENDING → LOADING → ACTIVE`，失败进 `FAILED`，卸载进 `UNLOADING → DISPOSED`（`fiber.ts:147-154`，`_getState` 判定在 `fiber.ts:580-585`）。状态迁移会发 `internal/status` 事件（`fiber.ts:592`）。
- **依赖等待**：Fiber 构造后对每个 `inject` 名字执行 `_checkImpl`（把当前可用的实现存进 `_store`，`fiber.ts:320-325,603-615`），再 `_refresh()` 计算 epoch：依赖齐了 epoch = `"版本:implUid:implUid…"`，缺依赖则 epoch = `INACTIVE`（`fiber.ts:617-628`）。
- **epoch 变化驱动装卸**：epoch 从 INACTIVE 变非 INACTIVE → `_reload()`（执行插件回调）；反向 → `_unload()`（`fiber.ts:630-646`）。服务注册/注销时 `ReflectService.notify` 遍历所有 Fiber 重算依赖并触发 epoch 变化（`reflect.ts:335-354`）——这就是「依赖就绪即自动装载、依赖消失即自动卸载」的实现。
- **_reload**：先把依赖快照进 `committed` 并在各实现的 `dependents` 集合里登记自己（`fiber.ts:681-686`），然后执行插件回调；失败则记 `_error` 进 FAILED（`fiber.ts:693-701`），**失败的 Fiber 只能靠显式 `update()` 恢复**（`fiber.ts:634,790`）。
- **_unload 的顺序保证**：先等自己提供的所有服务的 dependents 全部卸载完（自旋等待 + `_release` 回调唤醒，`fiber.ts:716-719`），再**逆序**执行本 fiber 的 disposables（`fiber.ts:720-730`），最后释放对各依赖实现的占用（`fiber.ts:732-736`）。即：**先卸消费者、后卸提供者**。
- **配置更新**：`fiber.update(config)` 走 `internal/update` waterfall，监听者可以不调 `next()` 从而**保留实例只改配置**，调 `next()` 则重启（`fiber.ts:783-819`）；候选配置先经 `internal/config` waterfall + schema 校验（`fiber.ts:676-679,50-62`），校验失败抛 `ValidationError`（`fiber.ts:19-36`）。
- **restart**：`_revision++` 后重算 epoch，等价「原地卸了重装」（`fiber.ts:768-774`）。
- Fiber 的 dispose 本身挂在父 fiber 的一个 effect 上（`fiber.ts:271-303`），实现「父卸载连带子卸载」；发布 `internal/plugin` 事件后才开始依赖解析（`fiber.ts:305-325`）。

### 1.4 effect：一切注册皆可撤销

- `fiber.effect(execute)` 立即执行副作用体，收集它返回的 disposer；fiber 卸载或显式调用 disposer 时**逆序**清理（`fiber.ts:69-73,424-567`）。effect 支持同步/异步 disposer、生成器批量注册（`fiber.ts:83-93,381-401`）。
- 事件监听（`events.ts:263-270`）、服务注册（`reflect.ts:291-292`）、日志 exporter（`logger.ts:236-242`）、工具注册（`packages/core/tools/src/index.ts:155-156` 的 `layers.effect(...)`）全部走这条路。这是 Cordis 最重要的纪律：**注册即 effect，卸载即逆序 undo**（deepseek-harness 根 AGENTS.md「Registrations are effects」）。

### 1.5 Service 基类与 provide

- `Service` 基类构造函数里直接 `ctx.reflect.provide(name, this, check)`（`service.ts:42-59`）——**类即服务，构造即注册**，随所属 fiber 卸载自动注销（`service.ts:8-9`）。
- `Impl` 记录含 `uid / name / ctx / dependents / value / check / isolate`（`reflect.ts:116-133`）；`provide` 的 disposer 要等所有 dependents 清理完才真正摘除实现（`reflect.ts:311-325`），配合 §1.3 的卸载顺序。
- `strict` 读：只有提供者 fiber 处于 `ACTIVE` 才对依赖者可见（`reflect.ts:251-257`）。

### 1.6 事件总线：五种分发模式

- 模式：`emit`（同步忽略返回值）/ `parallel`（全并发等全部，`Promise.allSettled`+`AggregateError`，`events.ts:191-196`）/ `serial`（顺序等，bail 即停）/ `bail`（同步顺序，bail 即停）/ `waterfall`（监听者包裹 `next()`，不调 `next()` 即否决后续与内建行为，`events.ts:31,246-261`）。
- 类型安全靠 **declaration merging**：包用 `declare module { interface Events { ... } }` 扩事件表（`events.ts:33-108`）；事件名是字符串，`internal/*` 是框架保留段（`events.ts:334-371`，含 `internal/plugin`、`internal/status`、`internal/service`、`internal/update`、`internal/commit`、`internal/config`、`internal/get`、`internal/set`、`internal/listener`、`internal/dispatch`）。
- 监听器带 `ctx` 与可选 `global` 标志，分发时按 context filter 过滤（`events.ts:118-122,162-171`）；`ctx.on()` 的监听器生命周期归属当前 fiber（§1.4）。
- `ctx.on/emit/plugin/provide…` 这些便捷方法不是 Context 自有方法，而是 `mixin()` 挂上去的 accessor（`reflect.ts:233-236,382-408`）。

### 1.7 配置体系

- 校验：插件 `Config` 是 StandardSchema 校验器，装载前同步校验（`fiber.ts:50-62`）；错误聚合为 `ValidationError`。
- intercept 链：`Service[symbols.resolveConfig]` 沿 intercept 原型链从祖先到自身收集配置段合并（`service.ts:86-102`）；`Config.merge` 存在时用语义合并，否则浅合并。
- 更新瀑布：`update()` → `internal/commit`（持久化通知）→ `internal/update`（保留实例或重启）→ 成功后发布 `effectiveConfig`（`fiber.ts:783-819`）。
- **volatile 配置**：schema 可返回 `Volatile<T>` 引用，消费方每次 `.get()` 读不可变快照；Loader 把纯 volatile 变更**直接写进运行中实例而不重启**并发 `loader/volatile-update`（README.md:103-105；`vendor/cosmokit/src/volatile.ts:9-12,39-45`）。

### 1.8 动态加载与 HMR（Rust 侧必须正视的部分）

- `Loader` 继承 `EntryTree`（配置树），持有 `ModuleLoader`——直接挖 Node 内部 ESM 加载器 `internal/modules/esm/loader`（或 `node-addon-require-builtin`），用它的 `import/resolve/loadCache` 在运行时装载 npm 包（`loader/src/index.ts:77-87,102`；`loader/src/internal.ts:55-102,131-143`）。配置项按 `cordis.yml` 的 Entry/EntryGroup 树驱动装载、禁用、提交（`loader/src/index.ts:104-174`）。
- HMR：chokidar 监听文件 → 从 Node `loadCache` 找到 ModuleJob 并经 `job.linked` 递归遍历模块依赖图（`hmr/src/index.ts:30-41`）→ 把变更文件分类为 accepted/declined → **从 ESM loadCache 删除缓存条目、重新 `import()`**（`hmr/src/index.ts:301-347`）→ `registry.delete(plugin)` 处置旧 Runtime、重新注册新实例（`hmr/src/index.ts:354-391`）。前提是 `--expose-internals`（`hmr/src/index.ts:79-81`）。
- 结论：这套「代码级热替换」的每一步都依赖 Node 的运行时模块系统与 JS 的动态性，是 Rust 不具备的地基（详见 §2.4 D3/D4）。

### 1.9 packages/core：内核之上组件怎么长出来

- **服务即组件**：核心服务都以 `Service` 子类注册到固定服务名——`agentLoop`（`packages/core/agent-loop/src/index.ts:317`）、`agents`（`packages/core/agent/src/index.ts:260`）、`sessions`（`packages/core/session/src/index.ts:1172`）、`systemPrompt`（`packages/core/system-prompt/src/index.ts:453`）、`tools`（`packages/core/tools/src/index.ts:112`）、`llm`（`packages/llm/llm/src/index.ts:378`）、`storage`（`packages/storage/storage/src/index.ts:54`）。
- **依赖声明**：`AgentLoop` 声明 `static inject = ['agents','sessions','llm','tools','systemPrompt','sessionProjections']`（`agent-loop/src/index.ts:291`）；`Agent` 只依赖 `sessionProjections`（`agent/src/index.ts:247`）；`ToolsService` 依赖 `systemPrompt`（`tools/src/index.ts:100`）——依赖图与包依赖图一致。
- **配置**：`static Config = z.object({...})`（schemastery，`agent-loop/src/index.ts:294-306`）。
- **扩展点即注册表**：`ToolsService.register()` 校验 output 契约与保留名，把工具插进 scope 分层注册表并返回 effect disposer（`tools/src/index.ts:127-157`；契约见 `tools/src/contracts.ts:30-46`：`execute(args, exec)` + 必填 `output { schema, render }`）；`SessionStore.registerMessageProjection()` 同构（`session/src/index.ts:1158-1170`）。可选依赖用 `ctx.get(name)`（如 `agent-loop/src/index.ts:320`）。
- **延迟装配**：`SessionStore` 构造时 `ctx.inject(['typert'], …)` 挂类型解析（`session/src/index.ts:1181-1190`）。
- **宿主启动**：`boot()` = `new Context()` → `ctx.provide('dshHomePath')` → `await ctx.plugin(Loader)` → prepare 钩子 → 挂 cordis.yml 配置树 → 等树稳定 → 启动审计；失败则 dispose 整树 fail-loud（`packages/boot/app-boot/src/index.ts:1226-1262`）。

## 2. 云悠组件内核设计

### 2.1 组件模型：Rust trait 与所有权设计

#### 2.1.1 概念映射表

| Cordis (TS) | 云悠 (Rust) | 说明 |
| --- | --- | --- |
| `Context`（Proxy 对象） | `Context`（普通类型，内部 `RwLock<ServiceTable>` + isolate/intercept 持久链） | Rust 无 Proxy，访问从属性读取改为显式方法调用（§2.4 D1） |
| 原型链子上下文 `extend()` | `Context::extend(meta) -> Context`（`Arc` 链表持久结构，子节点持父 `Arc`） | 语义等价：子共享父视图，父不被改 |
| `isolate(name, label)` | `Context::isolate(key, ScopeId)`，`ScopeId = NonZeroU64` | 同标签即同作用域，与 TS 一致 |
| `intercept(name, config)` | `Context::intercept(key, Value)`，配置载体 `serde_json::Value` | 合并顺序祖先在前，同 TS（`service.ts:86-102`） |
| `Plugin`（函数/类/对象） | `trait Plugin: Send + Sync`（`fn id() -> PluginId; fn inject() -> &[ServiceKey]; fn config_schema() -> …; fn setup(ctx, config) -> BoxFuture`） | 类/函数/对象三形态合并为一个 trait：Rust 里闭包、struct 都能实现它（§2.4 D5） |
| `Service` 基类 | `trait ServiceTrait`（生命周期钩子 `start/stop`）+ 显式 `ctx.provide::<T>(Arc<dyn …>)` | 取消「构造即注册」的魔法（§2.4 D5） |
| `Fiber` | `FiberHandle`（含状态 `watch::Sender<FiberState>`、JoinSet、CancellationToken、disposal 序列） | 状态机一比一平移 |
| 服务名 `ctx.counter` | `ctx.get::<dyn Llm>() -> Result<Arc<dyn Llm>>`（TypeMap：`TypeId::of::<dyn Llm>()` → `ArcEntry`） | 显式取用，错误显式返回 |
| 事件字符串名 | `EventKey(&'static str)` + 泛型 payload，事件表 `HashMap<EventKey, Vec<Listener>>` | 保留字符串事件段（`internal/*`），payload 用 `serde_json::Value` 或类型键（§2.4 D2） |

#### 2.1.2 所有权设计（对照 TS 的 retain-until-teardown）

Cordis 语义：服务实现要保留到所有 dependents 卸载完（`fiber.ts:712-746`、`reflect.ts:311-325`）。TS 靠手工 `dependents` 集合 + release promise 模拟；**Rust 用引用计数天然表达**：

- 服务条目 `ArcEntry { value: Arc<dyn Any + Send + Sync>, provider: FiberId, scope: ScopeId, dependents: RwLock<HashSet<FiberId>> }`；
- 服务表持 `Arc` **强引用**；**依赖方 Fiber 在 `committed` 里持 `Weak`**；
- 卸载提供者时服务表 drop 强引用 → 只要还有 dependents 持 `Weak` 升级成功，实例就活着；dependents 全部卸载（drop `Weak`）后实例自然析构；
- 语义等价于 TS 的 retain-until-teardown，但**释放时机由引用计数保证，不需要 TS 的 `impl.release` 手工协议**；仍保留 `dependents` 集合用于「卸载顺序：先消费者后提供者」的等待逻辑（对齐 `fiber.ts:716-719`）。
- 循环引用防线：**组件不得持有 `Arc<Context>` 强引用**。组件构造时拿到 `Weak<ContextInner>`（或仅持它需要的服务句柄）；`Context` 树本身由 root 强引用持有、与进程同生命周期，组件的 `Weak` 在运行期永远可升级。审计规则：`provide` 时组件若需回访 ctx，只允许 `Weak`。
- **Context 强句柄的唯一合法窗口 = `setup` future 执行期内**（2026-11-13 评审修订，云悠附议）：`setup(self, ctx, config)` 以值接收 `Context` 强句柄，仅用于装配期间提供子服务、注册 effect、派生子 context；**setup future 落定（ACTIVE）后，该组件实例与其创建的一切服务不得继续存留任何 `Arc<Context>` 强引用**，只允许 `Weak<ContextInner>` 或它依赖的服务句柄（`Arc<dyn Trait>`）。此规则写为 trait 契约注释的强制条款（见 §2.1.3），「服务实例持有 Context 强引用」列入**评审线一（云枢审架构）打回项**；lifecycle 测试须包含「setup 落定后 Context 强引用计数回落」的断言。

#### 2.1.3 内核 trait 草案（签名级，非实现代码）

```rust
// yunyou::plugin
pub trait Plugin: Send + Sync + 'static {
    fn name(&self) -> &str;
    /// 依赖的服务键（对标 static inject，agent-loop/src/index.ts:291）
    fn inject(&self) -> Vec<ServiceKey> { vec![] }
    /// 配置 schema（对标 static Config，StandardSchema → JSON Schema + serde）
    fn config_schema(&self) -> Option<JsonSchema> { None }
    /// 装载体（对标 apply / constructor）：返回的 future 完成即 ACTIVE。
    /// 【契约，强制】`ctx` 强句柄仅在本 future 执行期内合法持有：
    /// 落定后组件与其创建的服务不得存留 Arc<Context> 强引用，
    /// 只许 Weak<ContextInner> 或依赖的服务句柄（§2.1.2 评审修订条款）；
    /// 违者评审线一打回，lifecycle 测试断言强引用计数回落。
    fn setup(self: Arc<Self>, ctx: Context, config: ConfigValue) -> BoxFut<Result<FiberOutput>>;
}

// yunyou::context
impl Context {
    pub fn provide<P: Service>(&self, key: ServiceKey, svc: Arc<P>) -> Disposer;      // reflect.ts:291
    pub fn get<P: ?Sized + Service>(&self, key: ServiceKey) -> Result<Arc<P>>;        // reflect.ts:152/247
    pub fn on<E: Event>(&self, listener: impl Fn(&E) -> BoxFut + Send + Sync) -> Disposer; // events.ts:294
    pub fn plugin<P: Plugin>(&self, p: P, config: ConfigValue) -> FiberHandle;        // registry.ts:316
    pub fn extend(&self, meta: Meta) -> Context;                                      // context.ts:99
    pub fn isolate(&self, key: ServiceKey, scope: ScopeId) -> Context;                // context.ts:121
    pub fn intercept(&self, key: ServiceKey, cfg: Value) -> Context;                  // context.ts:139
}
```

- `Service` 约束：`Any + Send + Sync`，trait object 用 `dyn Trait` 时经 `TypeId::of::<dyn Trait>()` 做类型键（要求 `Trait: 'static`）。
- 服务 trait 定义在**消费方与提供方共同可见的契约 crate**（对标 dsh「capability seam 三角色：Service Definition / Service Provider / Consumer」，见 deepseek-harness 根 AGENTS.md），例如 `yunyou-llm` 定义 `Llm` trait，`yunyou-llm-openai` 提供实现——替换提供商即换注册，不动消费方。

#### 2.1.4 生命周期状态机（平移 §1.3）

`FiberState { Pending, Loading, Active, Failed, Unloading, Disposed }` 与 TS 完全一致（`fiber.ts:147-154`）；epoch = `Revision + 每个已就绪依赖的 (key, provision_uid) 序列`，依赖注册/注销 → 通知器扫所有 Fiber 重算 epoch → 触发 load/unload（对齐 `fiber.ts:617-646`、`reflect.ts:335-354`）。await 语义用 `tokio::sync::watch`（状态订阅）+ 保存首个错误（对齐 `fiber.ts:754-760` 的 `await()` 抛 `_error`）。失败 fiber 只能被显式 `update()` 复位（对齐 `fiber.ts:634`）。

### 2.2 依赖装配与配置注入

- **装配单元**：`Plugin`（对标 1.2）。装配动作只有两个：`ctx.plugin(p, config)`（启动）与 `ctx.inject(deps, cb)`（依赖就绪回调，对标 `registry.ts:300-302`）。
- **依赖等待**：`Pending` 态 Fiber 监听服务表变更；依赖的 `provision_uid` 序列变化即重算 epoch（§2.1.4）。
- **配置链**：`Context` 的 intercept 持久链 + 插件自带 config → 合并顺序：祖先 intercept 在前、自身在后（对齐 `service.ts:86-102`）；schema 校验失败即 `ValidationError`，装载中止（对齐 `fiber.ts:19-62`）。校验库用 **`serde` + `schemars`**（JSON Schema 生成），配置载体统一 `serde_json::Value`；`Config.merge` 语义合并按字段可配（对标 schemastery 的 merge 钩子）。
- **配置更新**：`FiberHandle::update(config)` → `internal/update` waterfall（监听者不调 `next()` 即保留实例）→ 或重启（对齐 `fiber.ts:783-819`）；持久化通知 `internal/commit` 保留。
- **volatile 热更新**：用 **`arc_swap::ArcSwap<T>`** 平移 cosmokit 的 `Volatile<T>`（§1.7）：消费方持 `Arc<ArcSwap<T>>`，loader 类组件原子换快照、发 `loader/volatile-update`，不重启（对齐 README.md:103-105）。这是 TS 机制里 Rust 可以**无损平移**的一块。
- **强类型与弱类型双轨**：内置组件走类型键（`ServiceKey::of::<dyn Llm>()`）；配置驱动的动态装配走字符串键 + 类型键注册表登记映射。两轨并存，禁止绕过类型键直接 `dyn Any` 下行转换散落在业务代码里。

### 2.3 异步运行时选型：tokio（多线程调度）

**选 tokio，理由（对着 Cordis 的真实需求逐条对）：**

1. **生命周期等待原语**：Cordis 的 `_unload` 要「等待 dependents 卸载完再继续」（`fiber.ts:716-719` 的 while + release promise）、`await()` 要等 inertia 排空（`fiber.ts:754-760`）——tokio 的 `watch`/`Notify`/`oneshot`/`JoinSet` 是这些语义的直接对应物，不需要自造。
2. **真实 I/O 面**：dsh 需要 LLM SSE 流式（HTTP 长连接）、子进程管理（bash 工具，对标 dsh 的 shell/subprocess 域）、文件监听（配置热重载，对标 hmr 的 chokidar）、定时器（对标 `@cordisjs/plugin-timer`）。tokio 全覆盖：`reqwest` + `eventsource-stream`、`tokio::process`、`notify`（配合 tokio）、`tokio::time`。
3. **取消传播**：dsh 工具契约要求异步工作观察 `exec.signal` 并静止后才落定（`tools/src/contracts.ts:30-46`）——对应 `tokio_util::sync::CancellationToken`，可层级派生，天然映射 fiber 树。
4. **生态与维护性**：async-std 已停滞、smol 生态薄、自造执行器是重复造轮子（全局规范第五条）。tokio 是事实标准且 dsh 场景没有 embedded/no_std 需求。

**运行时配置与纪律：**

- 多线程调度器（默认 worker 数）。**所有服务与插件 `Send + Sync`**——这是与 TS 的本质差异（TS 单线程事件循环天然无此约束），写进 crate 文档与代码评审项；单线程隔离需求（如某些状态机）用专用线程 + 通道，不引入 `!Send` 服务。
- **禁万能药**：服务表只允许一张 `RwLock`（内核内部）；服务实现内部不得为「借用检查过不去」而上 `Arc<Mutex>`（全局反骨清单案例）；跨服务共享只读状态用 `Arc` 不可变快照 + `ArcSwap` 热替换；可变状态归单个 owner（服务自身），暴露方法而非暴露锁。

### 2.4 与 TS 版差异清单（反骨审查：TS 怎么做 → Rust 为什么不行 → 替代与代价）

| # | TS 怎么做（证据） | Rust 为什么不行 | 替代方案 | 代价 |
| --- | --- | --- | --- | --- |
| D1 | Context 是 Proxy，`ctx.foo` 属性读取即服务解析（`context.ts:74`、`reflect.ts:143-219`） | Rust 无运行时对象代理；属性访问无法拦截 | 显式 `ctx.get::<dyn Llm>()` / `ctx.provide()`；「mixin 便捷方法」（`reflect.ts:233-236`）不保留 | 调用点多一层 `Result` 处理；换来无魔法、可 grep、错误显式。**可行，语义无损** |

| D4 | HMR：chokidar 监听 → 清 ESM loadCache → 重新 `import()` → 换 Runtime（`hmr/src/index.ts:301-347,354-391`） | 已编译机器码模块不可热替换；无 loadCache 等价物 | **实例级热替换保留**：同一 `ServiceKey` 换实现（dispose 旧 fiber → provide 新实现 → 依赖者自动重装载，epoch 机制已支持，对齐 `fiber.ts:617-646`）；**配置热更**走 update waterfall + ArcSwap volatile（§2.2）；**代码级热更**不做，开发期用「进程重启 + session 状态持久化」达到同等体验 | 代码级热更需重启进程（秒级）；换来无 `--expose-internals` 式黑魔法。**不可照搬，已替代** |
| D5 | `Service` 基类构造函数里自动 `provide`（`service.ts:42-59`）；`@Inject` 装饰器（`registry.ts:37-60`） | 构造函数副作用 + 装饰器魔法在 Rust 无对应惯用法（宏可模拟但徒增不可见控制流） | 显式 `ctx.provide(key, svc)`；依赖用 `fn inject()` 返回数组；如需装饰器体验，二期 `cordis-macros` 提供 `#[dsh::service(name = "llm", inject = ["tools"])]` | 每组件多 1-2 行注册代码；换来可见性。**可行** |
| D6 | 单线程事件循环：listener 无锁共享状态（全库隐含） | tokio 多线程下回调并发执行，`Fn(&E)` 共享可变状态会数据竞争 | 强制 `Send + Sync` 约束；分发模式语义保持（parallel 用 `JoinSet` 逐个隔离错误，对齐 `events.ts:191-196` 的 allSettled+AggregateError）；确需串行域的状态用 actor（mpsc）封装 | 服务作者必须考虑并发；不可妥协。**已明示** |
| D7 | `composeError` 把外层调用栈拼进异步错误堆栈（`utils.ts:275-288`） | Rust panic/backtrace 机制不同，跨 await 手工拼栈无意义 | `tracing` span 上下文 + `anyhow::Context` 错误链；错误结构含 fiber 名/服务键 | 堆栈形态不同但可诊断性更强（结构化）。**已替代** |
| D8 | `internal/get`、`internal/set` 代理瀑布钩子（`reflect.ts:163,204`） | 无 Proxy 即无读写拦截点 | 一期不实现；get/set 本身是方法，如需切面走「Resolver 管线 trait」（如 typert 类解析需求出现时再加） | 少两个扩展点；云悠一期用例不依赖它们。**明确砍掉，留升级口** |
| D9 | `WeakRef<Fiber>` 进日志 Message（`logger.ts:37`） | Rust 有 `Weak` 但日志记录持 fiber 弱引用意义有限（无 GC 观察者模式） | Message 持 `FiberId + 插件名` | 无实质损失。**已替代** |

**最小闭环启动序列**（对标 `boot()`，`app-boot/src/index.ts:1226-1262`）：

```
yunyou-cli::main
 └─ tokio::main → root Context
     ├─ ctx.provide(config)（yunyou-config 加载 yunyou.toml → 覆盖各组件默认 Config）
     ├─ 依序 ctx.plugin：llm → sessions → systemPrompt → tools(+内置工具) → agentLoop
     │   （Pending 等依赖；epoch 就绪自动 ACTIVE——顺序仅影响启动日志，不构成正确性依赖）
     ├─ agentLoop ACTIVE → 接收用户输入 → 一轮对话（流式输出 + 工具执行 + 会话事件落盘）
     └─ Ctrl-C → root.dispose()：事件循环停收 → 各 fiber 逆序 UNLOADING（先消费者后提供者）
         → disposables 逆序执行（工具子进程收割、LLM 连接关闭、存储 flush）→ 进程退出
```

验收口径：一条真实对话在会话文件里留下完整事件序列（user/assistant/tool_call/tool_result），重启进程能从 JSONL 恢复继续对话。

### 2.7 动态组件化演进路线（编译期注册 → 更彻底的动态化）

#### 2.7.1 演进阶段

- **阶段 1（本次方案落地）**：显式注册 + `yunyou.toml` 配置驱动装配；update waterfall、volatile（ArcSwap）、isolate/intercept 全量生效。已可做到：换 LLM 提供商、增删工具、改配置不重启（实例级动态）。
- **阶段 2**：`inventory`（或 `linkme`）声明式注册——三方插件 crate 链接进二进制即出现在注册表，`yunyou.toml` 按 `PluginId` 启用；`cordis-macros` 提供 `#[service]` 宏收敛样板。对应 Cordis 的「loader 配置树」体验，但**分发物仍是二进制**。
- **阶段 3**：**子进程插件协议**（对标 dsh 的 ACP/MCP/PTC 三种既有进程间模式）：内核定义 `PluginHost` trait，把「工具/事件/服务」三层经 JSON-RPC over stdio 桥接；宿主负责子进程生命周期（spawn/收割/超时），插件崩溃不伤宿主。MCP 作为该协议之上的一个 profile 集成（呼应业主决策：MCP 只是能力协议之一）。
- **阶段 4（远期，按需评估）**：WASM 组件模型（wasmtime + WIT 接口）承载不可信/跨语言插件，获得真正的沙箱化动态加载；内嵌脚本（rhai/quickjs）仅用于策略/过滤类轻扩展。
- **明确不做**：进程内 dylib 热加载（ABI 不稳，§2.4 D3/D4）；模拟 npm 的运行时源码编译装载（需要携带完整工具链，违背交付形态）。

#### 2.7.2 团队运行时（业主蓝图）与内核的边界

蓝图定性（`docs/需求/小Agent团队架构.md` 文首）：内核管**进程内**组件装配，团队架构管**多进程**运行时。逐角色划界：

| 蓝图角色 | 是否依赖 yunyou | 依据与理由 |
| --- | --- | --- |
| launcher | **否** | 蓝图六：「launcher 自身极简：能纯 std 就纯 std，不加载插件，只做进程管理和错误包落盘」；蓝图二-1「不加载插件，不依赖大 agent 运行时」。救援链要求 launcher 在内核都起不来时还能工作——依赖内核即自断后路 |
| 大 agent（Orchestrator） | **是**（完整内核 + 组件 + 团队组件） | 编排/审核/清账/花名册维护以**内核组件形态**挂进 Context（`team-orchestrator`），复用 fiber 生命周期与 effect 撤销（如花名册注册、审核队列监听随 fiber 卸载自动回收）；「不亲自干重活」（蓝图二-2）对应其 agent-loop 只编排不执行 |
| 员工型 worker | **是**（裁剪集） | 每个 worker 是独立进程 + 独立云悠实例：内核 + agent-loop + llm + tools + session；「可注入人设」（蓝图二-3）= 启动参数把人设文件注入 systemPrompt 组件配置，经 intercept 链合并（§2.2），不经任何代码分支特判 |
| 修复型 worker | **否**（代码路径上不出现内核服务解析） | 蓝图七-1：「启动路径上不允许出现读人设、读任务图、读花名册的代码分支。不是配置关掉，是代码里就没有」——同理，不加载插件就不链接内核；行为固定、最小权限（蓝图二-4） |
| 验证探针 | **否** | 蓝图八：「独立极简二进制，不依赖大 agent 运行时」 |
| 管理面板 | **否**（只读外部观测） | 蓝图二-5/七-5：观察面不是控制面；面板通过任务图只读副本与文件系统观察，写操作走 launcher 暴露的受控接口（§2.8 的对外接口文档范围） |

跨进程协作的硬边界：**worker 与大 agent 之间不共享内核事件总线**——通信只走任务图（SQLite + WAL，蓝图四-1）与文件系统（output/session_dir/错误包）。内核的 isolate/intercept 机制只在**单进程内**发挥作用；每个 worker 进程一个独立 root Context，人设注入即该进程 config 的组成，进程崩溃不影响他人（与蓝图「独立进程、独立会话目录、独立 workspace」一致）。任务图组件（team-taskgraph）本身是**双形态**：在大 agent 进程内作为内核组件提供审核/派活服务；worker 进程只经 rusqlite 直连访问，不加载该组件的编排逻辑。

与 §2.7 演进阶段的关系：阶段 3 的子进程插件协议（JSON-RPC over stdio）与团队运行时的进程模型**共用同一套进程管理底座**（spawn/超时/退出码/收割，蓝图八「launcher 内做超时 + 退出码检查」），实现时抽成共享库（`yunyou-util` 扩展或独立 `yunyou-procmgr`），避免 launcher 与阶段 3 各写一份进程管理。

### 2.8 接口文档策略（task-1 第 9 项，业主 2026-11-13 硬性要求）

背景：后续 App、Web 等端要接入云悠，所有对外接口（HTTP/WS/IPC）必须有机器可读规范 + 人工接口文档，落 `docs/接口/`。

**工具选型（云枢裁决）：**

| 接口面 | 机器可读规范 | 理由 |
| --- | --- | --- |
| 对外 HTTP（面板读写接口、未来 REST API） | **OpenAPI 3.1（YAML）** | 行业标准，App/Web 代码生成器齐全；3.1 原生支持 JSON Schema 2020-12，与组件配置 schema 同一套词汇 |
| WS / 子进程 IPC（worker↔launcher、未来阶段 3 插件协议、agent 事件流） | **JSON Schema draft 2020-12**（每消息类型一个 schema 文件） | WS/IPC 是消息流不是资源树，OpenAPI 表达别扭；JSON Schema 可独立校验每条消息 |
| SSE 流式响应（LLM 增量、事件流） | OpenAPI 内以 `text/event-stream` 描述 + 每事件负载引用 JSON Schema | 流的帧格式固定、负载可校验 |
| 组件配置文件（yunyou.toml） | JSON Schema（schemars 派生，与 §2.2 校验共用） | 配置即接口的一部分，校验器与文档同源 |

**真源与生成机制（防文档漂移，采用代码先行 + 门禁锁死）：**

1. **唯一真源是代码内的类型定义**：对外 DTO 用 `serde` + `utoipa` derive（HTTP）与 `schemars` derive（消息/配置）标注；rustdoc 注释里写语义契约（字段含义、取值范围、错误码）。
2. **生成物落盘入库**：`cargo xtask doc-api` 一键把 OpenAPI 3.1 与全部 JSON Schema 生成到 `docs/接口/openapi.yaml` 与 `docs/接口/schema/*.json`（生成物提交进 git，消费方不须先编译 Rust 即可拿规范）。
3. **门禁**：本地/CI 校验「重新生成的规范与落盘版本 diff 为空」，不一致即失败——改了类型忘了重生成过不了提交检查（对标 dsh 的 doc-sync/doc-gates 思路）。
4. **人工文档**：`docs/接口/<接口名>.md` 手写，内容限机器规范表达不了的部分：调用时序、鉴权、错误处置建议、示例；文件头必须链接对应 schema 文件，逐接口与生成物一一对应。

**接口变更同步纪律（四件套，同 commit 完成）：**

1. 改类型定义与 derive 注解（含 rustdoc 语义契约）；
2. 跑 `cargo xtask doc-api` 重新生成并提交生成物；
3. 更新对应人工文档条目；**破坏性变更**额外在文档头部「变更记录」段追加条目并标注迁移说明（对标 deepseek-harness AGENTS.md 的 upgrade-guide 纪律）;
4. 台账改动记录登记接口变更。

**内部组件接口**：不做额外文档体系——**rustdoc + trait 定义即文档**（`cargo doc` 全量发布到 `docs/接口/内部/` 可选）；内核 trait 的契约注释强制包含：前置/后置条件、失败语义、Send/Sync 约束、生命周期归属（对标 dsh verify-export-jsdoc 的「非显然契约必须有 JSDoc」）。评审线一（云枢审架构）把「trait 契约注释缺失」列为打回项。

## 3. 风险点（云枢自标）

1. **`Send + Sync` 纪律执行风险（高）**：TS 单线程假设被打破（§2.4 D6），服务实现里最容易顺手写 `Rc<RefCell>` 或跨 await 持锁。对策：yunyou 文档首屏写死约束；代码评审将「跨 await 持有锁/RefCell」列为打回项；提供 `actor`（mpsc 任务）模板给需要串行域的实现。
2. **弱引用释放时机的语义偏差（中）**：TS 在 dependents 全部卸载后还有 `impl.release` 显式回调（`reflect.ts:311-325`），Rust 的 Arc 析构没有回调位。若某组件需要「最后一个依赖者离开时执行收尾」语义，Arc 无法直接表达。对策：保留 `dependents` 集合与显式 release 通知（不依赖 Drop 时机），Drop 仅作为兜底；lifecycle 测试覆盖该路径。
3. **配置驱动装配的表达力缺口（中）**：一期没有 Loader 的 Entry 树（嵌套组、include、表达式插值，`loader/src/config/*`），`yunyou.toml` 只能平面声明。若首批组件配置需求超出平面结构，会在二期补「组」概念——方案里已按此预留 yunyou-config 的扩展位，但不承诺一期实现。
4. **waterfall 语义的 Rust 化复杂度（中）**：`internal/update` 的「不调 next() 即否决」闭包链（`events.ts:246-261`）在异步 Rust 里要用 `BoxFut` 链手工实现，容易写错重入（TS 里 `next()` 重复调用会抛错，`events.ts:254`）。对策：yunyou 内实现并配专项单测（重入、否决、短路三例）。
5. **范围蔓延风险（中）**：packages/core 里 agent-loop 实际 838 行主文件（`agent-loop/src/index.ts`），含大量 dsh 特有投影逻辑（runtime-context、session projection 等）。一期闭环只取「对话一轮」主路径，投影/恢复/压缩等推迟；该裁剪边界由本方案 §2.5 验收口径锁定，评审时请云悠确认。
6. **`dyn Trait` 类型键的对象安全约束（低）**：`TypeId::of::<dyn Trait>()` 要求 trait object 安全（无泛型方法、无 Self 返回）。契约 crate 设计时必须按 object-safe 规则写 trait（异步方法一律返回 `BoxFut`）。已列入契约 crate 的设计约束。
7. **团队运行时的「不依赖内核」纪律易被腐蚀（中）**：蓝图要求 launcher/修复 worker 代码路径上不出现人设/任务图/花名册逻辑（`docs/需求/小Agent团队架构.md` 七-1），同理不依赖 yunyou。Rust workspace 里加一条依赖毫无摩擦，纪律靠人守会漂移。对策（**已升为实现验收项**，2026-11-13 评审修订）：deny.toml + `cargo xtask deps-gate` 落地（§2.9 文件清单），**任务 2（内核实现）验收时必须实际跑通该检查**——黑名单内 crate 依赖 yunyou 或人设/任务图 crate 即 CI 失败，把物理隔离从纪律固化为机器门禁。
8. **接口文档漂移（中）**：规范生成物入库 + 门禁可挡住「忘了重生成」，但挡不住「改了行为没改语义契约注释」。对策：§2.8 四件套纪律 + 云枢审查线一把「接口行为变更但 rustdoc 契约未动」列入评审清单；首个对外接口（面板）落地时同步建 `docs/接口/` 骨架，避免文档体系后补。
