## 0. 结论速览

1. **官方实证修正一处**：官方 llm-retry 不是纯类型库——它本身是**插件**（`name='llm-retry'`、`inject=['agents','sessionProjections']`，`packages/llm/llm-retry/src/index.ts:21-22`，257 行），挂「agent loop 的请求恢复扩展点」并承诺「**每次调度重试在可取消等待前先持久化**」（index.ts:2-4 模块注释）；纯类型仅 48 行事件数据（types.ts:18）。路线图 P0-7「llm-retry 201 行类型建模」表述需按此校准：**类型建模与策略执行是两层，官方两层都真实存在**。
2. **形态终裁（与 lead 方向一致，本方案确认并细化）**：**retry 纯类型（RetryPolicy 参数集＋LlmFailure 分类）进 `yunyou-llm` 契约 crate＝插槽规格 v1 的一部分（主板）；重试策略执行进 bundled 插件 `yunyou-retry`＝第一张消费 P0-8 LlmFailure 的策略卡**。官方同构旁证：策略配置归属 provider 配置段而非重试插件（index.ts:24「This policy executor has no config; providers own retryPolicy」＋:33-34 配置错位即抛错）。
3. **超时三语义分层**：LLM 请求超时＝不确定结果**默认不自动重试**（白名单外，opt-in 才开）；工具超时＝协作式等静止（yunyou executor 现状已达标）；退避等待必须**可被取消信号打断**（AbortSignal 口径贯穿）。
4. **P1-11 沙箱排期终裁**：拆两段——**P1-11a（策略对象＋单后端最小沙箱）提前进一期受约束批**；P1-11b（多后端编译）留二期。理由见 §6。

## 1. 官方互证（三件，行号在案）

### 1.1 llm-retry＝请求恢复扩展点上的插件（不是库）

- 插件身份：`packages/llm/llm-retry/src/index.ts:21-22`（name/inject）＋`Config = z.object({})`（:28）——**执行器零配置，策略配置归 provider**（:33-34「retryPolicy belongs under each provider configuration」，错位即抛）。
- 类型建模（ResolvedRetryPolicy，index.ts:66-77 key 序列化反推全参）：`mode`（always/…）、`maxRetries`、`retryableCodes`（**错误码白名单**，sorted 参与键）、`initialDelayMs`、`maxDelayMs`、`jitterRatio`。
- 退避算法（:59-65 localDelay）：`initialDelayMs × 2^min(retry-1,1024)` 封顶 `maxDelayMs`，再乘抖动 `1±jitterRatio`。
- 下游结算（:45-57 DownstreamOutcome）：waterfall `next()` 的 decision 与异常统一捕获为两分支——重试判定不依赖异常穿透。
- 持久化纪律（:2-4）：「Each scheduled retry is **durable before its cancellable wait**」——先落盘再退避等待，取消不丢账。

### 1.2 tool-call-timeout-policy＝tools/execute wrapper（官方超时本身就是插件）

- `packages/guard/timeout-policy/src/index.ts:2-3`：「Cooperative tool-call timeout enforcer. A tool declares `timeoutMs` and promises to honor `exec.signal`; this wrapper arms that deadline…」——**工具声明预算、策略插件武装 deadline、信号替换后委托、仅自己计时器触发时改写结果**（:51-57：resolve caller-visible definition → temporarily replaces `exec.signal` → delegates → restores upstream signal → replaces result only when this wrapper's own timer fired，防误读其他 wrapper 的计时器）。
- 结论：官方「超时」与「重试」都是插件卡；工具侧只负责声明与协作。yunyou 的对应现状：工具执行器已实现超时/取消 select＋等静止不 abandon（executor.rs，插件化方案 §5.1 已证）——**工具侧超时骨架达标，per-tool timeoutMs 声明随 S4（P0-9）落**。

### 1.3 与 yunyou 契约面的咬合点

- P0-7（retry-policy 纯类型）与 P0-8（LlmFailure 结构化）在路线图是两张 0.5d 独立卡、同落 `yunyou-llm` 契约 crate——本设计把它们合并为 **S9 一批**（类型与失败分类必须同批冻结，否则 retryable_codes 白名单无锚点）。
- 消费点：yunyou 一期无 waterfall 六事件，等价位＝**agent-loop 的 LLM 流失败处理**（turn.rs stream_once 失败路径）——插件 provide 策略服务，agent-loop inject 消费（插件化方案 §2.3 服务注入映射，零新增机制）。

## 2. 插件形态（终裁）

```
主板（规格层）：yunyou-llm 契约 crate
  ├─ LlmFailure（结构化失败：错误码/类别/事实保留）        ← P0-8
  └─ RetryPolicy（参数集）＋ classify(failure)->RetryAction ← P0-7（RetryAction = Retry{delay} | Fail）
卡（策略层）：yunyou-retry bundled 插件
  ├─ provide: dyn RetryPolicyProvider（按 LlmFailure 给出 Retry{delay}|Fail 决策）
  ├─ 消费: 无（策略自足）；被消费方: agent-loop（inject）
  ├─ config: RetryConfig（§5，default 全预置）
  └─ 退避执行: 指数+抖动（官方 localDelay 同构），等待期 select! 取消信号
消费方：agent-loop
  └─ stream_once 失败 → ctx.get::<dyn RetryPolicyProvider> → classify → Retry{delay} 则退避后重发
```

- **为什么 agent-loop 强依赖 inject（bundled 恒在）而非可选 get**：bundled 两级语义（插件化方案 §2.2）＝随框架分发、不可卸载；一期策略卡恒在，消费点无需可选分支（可选化留 market 化时降级，二期）。
- **服务键**：`ServiceId::of::<dyn RetryPolicyProvider>()`（yunyou-llm 契约 crate 内定义 trait——契约 crate 归属规则，内核方案 §2.1.3「契约 crate 三角色」）。
- **与 llm-openai 的关系**：不装饰 `dyn Llm`（ServiceDuplicate 冲突且违反「策略归调用侧」）；llm-openai 保持纯 provider，重试在其上游调用点。

## 3. 重试语义规格（分类表＋退避）

### 3.1 失败分类表（LlmFailure 类别 → 默认动作）

| 失败类别（LlmFailure.code 族） | 默认动作 | 理由 |
| --- | --- | --- |
| 连接失败（connect/dns/握手） | **重试**（白名单内） | 幂等：请求未达上游 |
| HTTP 5xx（上游错误） | **重试**（白名单内） | 上游瞬态；POST 已发但失败归上游 |
| HTTP 429（限流） | **重试**（白名单内，退避上限更高） | 官方 429→等待语义；注意豆包限流业主令＝串行单发，退避基数取大 |
| HTTP 401/403（鉴权） | **不重试**（Fail 直出） | 任务17-⑦ 实证：重试无意义且掩盖配置错误 |
| 请求 4xx（schema/参数错） | **不重试** | 确定性失败，重试=重复付费 |
| **本地超时（timeout_secs 耗尽）** | **不重试**（默认；`retry_on_timeout=false` 显式 opt-in） | 请求可能已达上游：重试=可能双计费/双副作用——「不确定结果不自动重试」为本设计安全默认律 |
| 流中断（SSE 半途断连，无 content 落盘） | **重试**（白名单内） | 本轮无产出，重发幂等 |
| 取消信号触发 | **不重试**（直接 Fail→上层取消语义） | 取消是用户意志，不是故障 |

### 3.2 退避与预算

- 退避：`initial_delay_ms × 2^min(attempt-1, 上限指数)` 封顶 `max_delay_ms`，抖动 `1±jitter_ratio`（官方 localDelay 同构，防惊群）。
- 预算：`max_retries`（默认 2，即最多 3 次尝试）；**预算永不放宽以接受劣化**（性能专项纪律沿用）。
- 可观测：每次重试决策经 TurnObserver 事件面（`RetryScheduled{attempt, delay_ms, cause}`）＋tracing 日志；**durable-before-wait 折中**：一期重试决策不落 JSONL（会话日志禁 append 新 type——官方 ignorable 纪律，插件化方案 §3-⑧ 注），落 observer/日志层；JSONL 持久化随二期 request-header 事件（P0-4）扩展评估。

## 4. 超时语义与取消信号（AbortSignal 口径）联动

| 层 | 超时语义 | 取消语义 | 现状/动作 |
| --- | --- | --- | --- |
| LLM 请求 | `timeout_secs`（llm config，已有）＝请求预算 | 取消＝用户意志，**退出重试循环且不重发** | R2（插件化方案 §5.1）：Llm::stream 签名补取消令牌，**与 S9 同批**（trait 一次破坏性变更） |
| 重试退避等待 | 退避 sleep 非独立超时 | **退避等待在 select! 中与取消信号竞争**，取消即中止整个重试链 | S10 实现 |
| 工具执行 | `tool_timeout_secs`（agent-loop config）＋S4 的 per-tool `timeoutMs` | executor 已等静止不 abandon（取消语义达标） | 已达标；timeoutMs 声明随 S4 |
| 会话轮 | 取消＝本轮终止 | run_turn 内合并调用方与 fiber 取消（R1，一期 S7） | 插件化方案 §5.1 既定 |

联动铁律三条：①取消信号优先级高于一切重试决策（取消链上不产生新尝试）；②超时触发的失败在分类表里是独立类别（不与网络错误混类——分类精度依赖 P0-8 LlmFailure 结构化的 code 族设计）；③重试计数与超时预算独立（退避不挤占 timeout_secs 预算，各自计时）。

## 5. 可配置 schema（schema default 预填＝官方「装好即预置」律）

```toml
[retry]                            # yunyou-retry 插件段（S2 的 [plugins] 机制接管）
enabled = true                     # default true：装上即有合理重试行为
max_retries = 2                    # 最多 3 次尝试
retryable_codes = ["connection", "http_5xx", "http_429", "stream_interrupted"]
                                   # 白名单驱动（官方 retryableCodes 同构）；timeout 显式排除
initial_delay_ms = 500
max_delay_ms = 8000
jitter_ratio = 0.1
retry_on_timeout = false           # 安全默认律：不确定结果不自动重试
```

- **default 即产品**：零配置装上＝连接失败/5xx/429/流中断自动重试 2 次、指数退避 0.5s→8s 带抖动、超时与鉴权错误不重试——用户不填任何字段得到正确行为（官方「装好即预置」律，插件化方案 §3-④）。
- **volatile 热调**：`max_retries`/`retryable_codes`/`enabled` 走契约⑧ volatile-update（S6 底座）——改白名单不重启插件（限流调参高频场景）。
- **凭据无关**：本插件不触凭据（契约⑤零交集）。

## 6. P1-11 sandboxPolicy 排期终裁（D-17-1 实证后）

**裁决：拆两段，P1-11a 提前进一期受约束批。**

| 段 | 内容 | 排期 | 理由 |
| --- | --- | --- | --- |
| P1-11a | **策略对象＋单后端最小沙箱**：bash 子进程经沙箱执行（可写根＝workspace root_dir，文件系统可见性收窄；策略对象 trait 化为契约⑨的 Rust 载体） | **一期受约束批（S2/S5/S8 之后、B 线全链闭环后动工）** | ①任务17-⑥ 实证：path_guard 只守文件类工具，bash 重定向绕过层——**门禁层无法根治进程类工具**；②云织短期文本门禁（池 task-8）＝可绕过止损（变量/引号/base64 编码即绕），仅买时间；③官方把沙箱当工具授权前提（契约⑨，对标地图 §C profiles.ts:17-56）；④一期验收「开关拨下不留残尸」的信任前提＝工具在授权范围内执行 |
| P1-11b | 多后端编译（bwrap/Landlock）＋进程内栅栏单源 | 二期（路线图原位） | 多后端是加固非止血；单后端先立策略对象，接口不返工 |

- 一期范围控制：P1-11a 只保「bash 子进程文件系统可见性收窄」最小面，**不做网络隔离**（LLM 中转在宿主侧，工具面暂无网络需求面）、不做 seccomp。
- 后端选型列待裁决 D9（Landlock＝内核原生无依赖 vs bwrap＝容器化强隔离，倾向 Landlock 起步）。
