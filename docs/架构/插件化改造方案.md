## 0. 结论速览

1. **内核缝已基本齐备**：M2 内核（yunyou crate）已具备插件模型的全部生命周期底座——Plugin trait（registry.rs:24-50）、epoch 驱动装卸（load.rs:56-91）、effect 逆序撤销（effect.rs 全文）、fiber 级取消令牌（fiber.rs:99/202）、装配失败整树卸载（load.rs:244-265）。**插件化一期对内核是「补声明面」不是「补机制」**：缺 manifest 元数据、volatile 配置底座、事件面最小集、凭据服务、UI 注册缝。
2. **硬编码只剩一处主战场**：装配序列（yunyou-cli/src/assemble.rs:30-56 五插件逐个写死）＋配置面（yunyou-config/src/model.rs:20-33 DshConfig 强类型五段且 `deny_unknown_fields`）。这两处是主板论的直接违反点，一期改造核心。
3. **组件形态已经就位**：四个组件 crate（llm-openai/session/tools/agent-loop）均已实现 Plugin trait 且 setup 内 provide 服务（`*Plugin` 结构体）——它们是「bundled 插件雏形」，一期给它们补 manifest 声明即完成形态升级，**不需要推倒**。
4. **12 条契约**：①工具注册=已有；②工具→模型桥=已有（隐式）；⑦生命周期底座=已有需贯穿；③⑥需改造（section 机制/output 强制，与 P0-6/P0-9 合并）；④⑤⑧⑩⑪需新建；⑨部分（path_guard 在、sandboxPolicy 缺）；⑫P1 可选。逐条映射见 §3。
5. **热插拔标准**：逆序撤销已有；「代际门」在 fiber 自身装卸层已有（load.rs:71-77 superseded 判定＋effect.rs:102-107 已处置拒绝注册），缺「跨 await 写回点」的组件侧代际守卫；AbortSignal 贯穿缺「对话轮取消与 fiber 卸载取消合并」与「LLM 流/工具执行全链传递」两处（§5）。
6. **P0×12 合并裁决**：P0-6（system-prompt 四件）、P0-9（ToolDefinition 五点核对）并入插件化一期（它们本身就是插槽规格的冻结内容）；P1-1/P1-2 的最小版（凭据引用＋secret 脱敏）并入一期（契约⑤的最低实现）；其余 P0 保持独立卡，但实现必须按插件边界。逐项裁决见 §6.3。
7. **验收口径**（业主定）：每个机制的终态形态=「可以在面板上被开关」。一期验收=六 bundled 插件 manifest 就绪＋yunyou.toml 可禁用非核心插件并安全启动＋开关拨下不留残尸。

## 2. 插件模型设计

### 2.1 主板与插槽（铁律映射）

```
┌────────────────────────────────────────────────────────────┐
│ 主板：yunyou 内核 + 宿主（yunyou-cli / 未来 App 网关）        │
│  插槽规格 = 内核契约 12 条（§3）＋ UI 注册缝（§4）            │
│  规格冻结 = 契约 v1 发布即冻结，改规格=发 v2 并写迁移（§2.5）   │
├────────────────────────────────────────────────────────────┤
│ 卡（插件，两级）：                                            │
│  bundled（内置不可卸载）：llm-openai / session / tools /      │
│    system-prompt / agent-loop ＋ 后续 compaction/persona 等   │
│  market（社区可卸载）：yunyou-media 式独立包，dsh plugin add  │
└────────────────────────────────────────────────────────────┘
```

- 主板只提供插槽规格：内核不 import 任何插件 crate 的实现类型（现状已成立：组件间只走 `ctx.get` 服务边，内核不依赖组件——内核方案 §2.6 依赖规则 1）。
- 「什么都可以换」的实证路径：换 LLM 提供商=换 provide `dyn Llm` 的插件；禁用工具=禁用 tools 插件或注销单个工具（register 返回的 disposer）；人设/压缩等新机制一律以插件进场，严禁进 assemble.rs。
- 插件对接插件=Context 服务注入（铁律第 4 条）：消费方 `inject()` 声明依赖服务键，内核 epoch 机制保证「依赖就绪才装载、依赖消失即卸载」（load.rs:56-91）——compaction 消费 llm 服务、workflow 消费 tools 等未来组合零新增机制。

### 2.2 插件两级与 manifest

**两级定义**（铁律第 3 条）：

| 级 | 装载形态 | 分发 | 卸载 | Rust 载体 |
| --- | --- | --- | --- | --- |
| bundled | 编译期注册，随二进制分发 | 框架本体 | **不可卸载**（只可禁用） | 组件 crate 内 `*Plugin` 结构体＋清单登记 |
| market | 二期子进程插件协议（内核方案 §2.7 阶段 3：JSON-RPC over stdio） | 独立包（`dsh plugin add file:`/tgz） | 可卸载 | 插件宿主进程，manifest 文件随包 |

**manifest（插件声明面，一期最小集）**——一期以「代码内声明＋schemars 生成落盘」双形态存在（与内核方案 §2.8「代码是真源、生成物入库」同构；文件形态留给 market 级，列待裁决 D1）：

```text
PluginManifest {
  id: "yunyou-tools"            // 全局唯一；bundled 用 crate 名，market 用包名
  version: "0.1.0"              // 插件自身版本（semver）
  level: bundled | market       // 两级；bundled 禁用仅影响启用态，不影响分发
  contracts: ["tools.v1"]       // 对齐的插槽规格版本（§2.5 契约版本化）：自供+消费合集
                                //（S1 审查裁定 2026-11-13；消费视图可由 inject∩contracts 派生）
  provides: ["dyn RegistryService"]  // provide 的服务键（字符串投影，供面板/诊断展示）
  inject: ["dyn Llm", …]        // 与 Plugin::inject() 同源，manifest 侧冗余声明供装载前静态校验
  config_schema: (schemars 派生)  // 已有 config_schema() 基座（registry.rs:40-42）
  ui: []                        // UI 注册缝贡献（§4；一期可为空数组=预留位）
  auto_enable: true             // bundled 默认启用；yunyou.toml [plugins] 可覆盖
}
```

落地方式：`Plugin` trait 增补 `fn manifest(&self) -> PluginManifest`（默认实现由 name/version 推导最小值，存量组件逐个补全字段）。宿主启动时先读全部 manifest 做静态校验（inject 冗余声明与 trait 声明一致性、contracts 版本兼容、服务键拼写），再进入装配。

> 注记（S1 审查同步，2026-11-13）：①**config_schema 不进 manifest 结构**——由既有 `Plugin::config_schema()`（schemars 派生）承载，避免 schema 字符串化损耗；②服务键字符串一律经 `projection_of::<P>()` 投影生成并与 `ServiceId::of::<P>()` 同类型参数，装载前校验凭进程级投影表反查比对（S1 已落地：yunyou/src/manifest.rs，300 行含漂移反例 DriftSvc 测试）。

### 2.4 装配序列改造（主战场）

现状 `assemble.rs:30-56` 五插件逐个写死。改造为**表驱动装配**：

```text
1. 内置插件注册表（bundled 清单，编译期常量）：
   [OpenAiPlugin, SessionPlugin, SystemPromptPlugin, ToolsPlugin, AgentLoopPlugin]
2. 读 yunyou.toml [plugins] 段：每插件 { enable: bool = manifest.auto_enable, config: 段值 }
3. 循环：for entry in 清单 → ctx.plugin(entry.plugin, 段配置)（禁用者跳过并记日志）
4. 逐个 await_ready；失败整树卸载 fail-loud（沿用 await_or_teardown，assemble.rs:60-66）
5. 启动后输出插件状态表（id/version/enabled/state）——面板可开关的 CLI 观测面
```

- 装配层从「知道每个插件」降级为「知道清单接口」——新增内置插件只改清单一处，不再改装配代码。
- `run.rs` 仅 ③ 步换实现；就绪标记/横幅/REPL 逻辑不动（run.rs 现有七步结构保持）。
- **B 线冻结注记（裁决 D4，lead 2026-11-13 收紧）**：assemble.rs 属 yunyou-cli（B 线审查对象 crate），本改造动工排期**必须排在 B 线全链闭环（修复＋复审＋live 验收＋提交）之后**——云门修复正动 assemble.rs，先行即撞；yunyou-config 两文件同在 B 线清单，**S5 的 config 接线同受此约束**。批次划分：先行批=S1/S3/S4/S6/S7（yunyou/system-prompt/tools/llm 域），受约束批=S2/S5/S8（§7 风险 1）。

### 2.5 规格冻结与版本化演进（铁律第 2 条）

- 契约面（12 条＋UI 缝）以 **v1** 发布：本方案过审即 v1 冻结点；此后任何破坏性变更（改签名、删字段、收紧语义）必须发 **v2** 并保留 v1 兼容期，manifest `contracts` 字段声明兼容版本区间（semver range）。
- 插件声明 `contracts: ["tools.v1"]`，宿主装载前校验：插件要的版本宿主板不提供 → 拒装并明确报「插槽版本不符」，不静默降级（对齐官方 plugin-manager 的兼容性评估：`packages/boot/plugin-manager/src/index.ts` evaluatePluginCompatibility/版本豁免机制，1458 行域）。
- 文档纪律：契约 v1 全文落 `docs/接口/`（schemars 生成 JSON Schema＋人工契约文档），按内核方案 §2.8 四件套同步，防「规格悄悄改」。

## 5. 热插拔标准落地

> 铁律第 5 条：开关拨下＝登记资源逆序撤销＋在途请求收取消＋代际门挡 stale——拔卡不断电、开关不留残尸。三要素现状与改造点：

### 5.1 逆序撤销＋AbortSignal 贯穿

**已有**：effect 逆序清理（load.rs:287 `into_iter().rev()`）；panic 隔离（单 disposer 失败不阻断其余，load.rs:288-295）；工具执行器取消语义（executor.rs：cancel 触发→返回 tool/cancelled，**等工具 future 静止不 abandon**——对齐官方 contracts.ts:32-46「settle only after its owned work reaches quiescence」）。

**缺口与改造点（两点，R1/R2）**：

- **R1 取消源合并**：对话轮取消（REPL Ctrl-C 传入的 CancellationToken）与 fiber 卸载取消（FiberShared.cancel，fiber.rs:99）是两条独立线。插件被禁用时，正在跑的对话轮**不会被取消**——这就是「残尸」的具体来源。改造：`AgentLoop::run_turn*` 内部以 `tokio_util::sync::CancellationToken` 的 child token 合并两源（调用方 token.child_token() ＋ fiber.cancellation()），任一触发即整轮收流。改动点：agent-loop/plugin.rs（LoopService 持 fiber 句柄或注入 fiber cancel）＋turn.rs 取消检查点。
- **R2 服务异步面贯穿**：Llm::stream 请求不接收取消令牌（turn.rs 的取消检查只在循环边界 select，LLM 流式读取本身不感知）。改造：Llm trait 异步方法签名增补 cancel 参数（或 ToolExec 式上下文结构体），llm-openai 的 SSE 读循环 select 该令牌——工具侧已达标，LLM 侧是最后一块。**术语裁定**：实现载体沿用 tokio CancellationToken（内核方案 §2.3 既定），文档与契约口径统一称「取消信号（AbortSignal 语义）」，映射表写进契约 v1。

### 5.2 epoch 代际门（防 stale 异步写回）

**已有（雏形即内核层代际门）**：

- 装卸任务被超越判定：epoch 更新先于 busy 检查，任务收尾时 epoch 不符即交接反向任务（load.rs:71-77「若 busy 时跳过记录，装载完成会用旧 epoch 误判 settled，留下幽灵 Active」——内核层代际门已实测在位）；
- 已处置 fiber 拒绝注册：effect_with 检查 `uid.is_none()`（effect.rs:102-107「fiber 已处置，拒绝注册 effect」）——stale 注册的直接防线已有。

**缺口与改造点（G1/G2）**：

- **G1 跨 await 写回守卫**：组件在异步任务（如配置刷新、外部事件回调）收尾时向注册表写回——若期间本 fiber 已被卸载/重启，写回即 stale。内核补一个守卫 API：`FiberHandle::generation() -> u64`（读 revision）＋惯用法「发起前记 generation，写回前比对，不一致即丢弃」。effect_with 的 uid 检查覆盖「注册即 effect」路径，G1 覆盖「跨 await 后的手工写回」路径（如未来 compaction 插件刷新 section 的场景）。
- **G2 门禁化**：代际守卫靠自觉会漂移（同内核方案风险 7 的教训）。对策：审查线一把「异步任务持有 fiber 代际未比对即写回注册表/provide」列为打回项；lifecycle 测试补「卸载后迟到的写回被拒」用例。

### 5.3 热插拔验收口径（一期）

1. 禁用 tools 插件启动 → agent-loop Pending（inject 缺依赖），诊断输出「依赖未就绪」而非崩溃；重新启用 → epoch 就绪自动 ACTIVE（内核机制零改动直接达标）。
2. 运行中禁用（二期形态，一期以 dispose 演练）：在途工具执行收取消（executor 等静止）、注册表条目随 effect 逆序清空、无孤儿服务。
3. 开关不留残尸：卸载后 `RegistryService::schemas()` 不含已禁用工具；强引用计数回落（lifecycle 既有断言扩展）。
